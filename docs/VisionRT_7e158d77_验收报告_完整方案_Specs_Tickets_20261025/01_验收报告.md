## 待修与补验

### C01 · P1 · 关闭没有提交异步重置，运行时内部Python owner可能使关闭永久等待

证据：[src/ui/AppController.cpp#L650-L766](https://github.com/QWERDF007/VisionRT/blob/7e158d77375a7141aab5e2231956161870576161/src/ui/AppController.cpp#L650-L766)。

删除同步clearResults是正确的一半，但672行仍用pending != Pending::Close排除关闭；requestReset只在该分支内调用。Close清理的是UI引用，运行节点的ResultSlot和实例没有经过coordinator reset。749行仍直接在GUI调用python->prepareShutdown；随后检查storage.active。存活的运行节点输出足以使active不为0，并非只有外部引用。poll在closing/pendingClose时只查isCloseReady并return，不再执行其他管理推进。

**触发/证据边界：**Python工具生成np.ndarray，执行结束后Runtime ResultSlot保留图像；不手动Reset，直接关窗。UI引用清掉后slot仍保活，prepareShutdown不会清该slot，关闭等待不到计数归零。慢Python release还会由prepareShutdown的activeTools循环在GUI执行。此结论来自完整调用/引用链，未在本环境Qt复现；不能写成所有工程都必现。

**改进：**关闭获准后先进入Closing，再提交现有requestReset管理命令；继续消费runtime完成事件，直到coordinator在锁外reset实例与slot并通知完成，才清UI残余owner和prepareShutdown。给关闭增加一个小型阶段枚举（Resetting/AwaitOwners/Ready），poll只在AwaitOwners走owner等待分支，不能所有closing一律return。不要只把原if条件去掉或提前设closing而留下早退，亦不要恢复同步clearResults。

**验收：**已运行Python图像工具直接关闭，无外部引用应完成；另外保存Mat/ROI外部owner，稍后GUI事件释放后能自动关；慢release期间GUI心跳持续；重复关闭只发一次closeReady；测试不得先resetRuntime清结果再关窗。

### C02 · P2 · 阶段时间只到模型未到画布，异常耗时标志也遗漏

证据：[src/ui/qml/FlowCanvas.qml#L612-L617](https://github.com/QWERDF007/VisionRT/blob/7e158d77375a7141aab5e2231956161870576161/src/ui/qml/FlowCanvas.qml#L612-L617)。

DurationText和nodes新增prepare/init/validate字段，但FlowCanvas仍只显示timingOperatorText、timingPreprocessText、timingPostprocessText，后三个真实阶段字段没有QML消费者。新measured标志置于prepare/validate正常结束后；ScopeTimer异常析构仍记录耗时，标志却保持false，导致实际执行并失败的阶段显示未测。

**触发/证据边界：**成功运行后悬浮节点，仍看不到准备/初始化/校验；输入或输出校验抛异常时，已消耗时间的阶段被标未测。initMeasured还用deferredCreateMs>0推断是否执行创建，不能用时间大小表达阶段是否执行。

**改进：**沿现有tooltip样式增加宿主准备、初始化、结果校验行，并消费相应字段；算法内部预/后处理没有上报继续—，不冒用宿主指标。把是否测量与ScopeTimer进入/结束绑定，正常或异常退出均完成测量；未进入保持false，真实0合法。

**验收：**真实QML悬浮核对三字段；准备失败、初始化失败、输出校验失败、热运行、真实0及未进入阶段分别断言。结果失败不代表该阶段未测，Python桥接子项不得重复加到Adapter耗时。

### C03 · P2（条件性行为缺口） · DrainGuard只约束部分路径，排队请求被统一静默清除

证据：[src/ui/AppControllerReadback.cpp#L21-L128](https://github.com/QWERDF007/VisionRT/blob/7e158d77375a7141aab5e2231956161870576161/src/ui/AppControllerReadback.cpp#L21-L128)。

成功消费信箱末尾有!draining，但异常分支81行仍无条件updateReadback，且updateReadback入口不检查draining；它还能处理SaveRequest及ACK。requestOutputText的guard能阻止新文本任务，因此不应再泛称必然启动新文本。另45行readRequests.clear同时丢弃TextRequest与SaveRequest，缺请求完成/取消结果。DrainGuard析构固定设false，在同步信号造成嵌套时不保留外层状态。

**触发/证据边界：**排空时遇到格式化异常且存在待办请求，可进入读取派发/保存路径；成功路径则统一清空待办。这里不声称普通关闭必然丢失保存，只指出当前通用排空API对这类可构造组合缺明确保证。

**改进：**统一在调度入口拦截draining，结果消费只完成交付不再驱动新派发；异常/成功路径相同。按管理目的处理队列：已有导出或保存明确完成、取消或保留，不能把清队列当成功。保存与文本请求至少按现有variant区分，无需新框架。guard保存并恢复旧值，或明确拒绝重入。

**验收：**排空+异常+多个请求，以及outputTextReady同步触发另一次管理操作：无新读者/意外保存/提前ACK；每项请求有确定结果，已完成导出交付一次，嵌套结束仍保留外层draining。

## 关闭问题的完整因果链

`Pending::Close` → 跳过requestReset → 仅清UI快照 → runtime.nodes[*].slot仍保留DataRef<Image> → NumPy owner计数仍非0 → prepareShutdown后等待isCloseReady → poll只重复查计数 → 未发生slot清理，无法进展。

PythonRuntime::prepareShutdown会释放activeTools并清loader，但不会访问RuntimeEngine节点slot。RuntimeEngine::manage(Reset)才会调用NodeRuntime::reset并清slot；当前关闭没有提交它。即使用户没有保存外部Mat，也可能触发该问题。不要把所有剩余引用统一称“外部资源”。
