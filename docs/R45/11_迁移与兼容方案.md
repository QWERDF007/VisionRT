# 一次性迁移与发布方案

## 不只是 UI 排序改动

R44 只依赖名称和数组顺序，无需协议升级；本轮决定运行时/工程按数字参数编号，这是真正的接口变更。目标版本 ABI9、声明 schema6、工程 format7 是新协议标记，不代表已发布。ValueJson 的值布局及零拷贝所有权继续沿用，module_index 若结构未改就不无故升 schema，但其中的 ABI/声明引用必须对应新产物。

发布后不同时支持 string/int 两套运行时端口键，也不永久保留 id→name→value 适配层。旧资产在工具入口之外一次性转换，输入文件保留，输出写到新目录。项目只做当前打开文件的明确转换/另存，不能后台批量覆盖用户全部工程。

## 迁移矩阵

| 资产 | 改造 | 不能做 |
|---|---|---|
| 固定工具声明 | 每方向旧 name_en→新 id；保留当前显示顺序；设置 next；可保留别名 | 运行时按当前行号临时编号 |
| native 模块 | 按同一映射更新参数子类、输出包装、工具常量，重新编译 ABI9 | 只改声明就加载 ABI8 DLL |
| Python 工具 | inputs/outputs改 int 键；SDK result/pack公共号；调整全部helper与工具 | 将数字转换回name作为长期隐藏适配 |
| 关系/interaction | 源工具和helper各用自身映射，写结构化PortRef | helper/input/output编号跨方向混查 |
| 工程字面值/绑定/签名 | 目标输入查目标节点映射；source端口查源节点映射 | 按目的节点的同号猜来源 |
| 动态表达式/条件 | 用旧节点具体契约生成本地映射；保留symbol/公式；方向独立高水位 | 用打包静态声明覆盖动态端口；替换公式文本为数字 |
| ExecutionGuard/Receiver/Select | 只改其端口引用；已有模式、node/flow身份保留 | 把整个执行条件配置当成普通端口id |
| UI虚拟参数 | 保留现有配置项语义，真实端口context才用PortId | 将“执行条件/合流类型”等编辑动作盲目编号 |
| 输出文本 | 对应参数id显式写条目；单值复制行为保持 | 新增诊断JSON菜单或重新拼节点错误信息 |
| 示例/fixtures/测试断言 | 所有合法夹具对齐新协议，旧ABI/旧键反例保留用于拒绝测试 | 把明确反例当成死代码删掉 |

## 生成一次迁移映射

为每个工具建立一份可审阅映射，公共端口按固定规则转换。没有作者指定编号时，可按迁移前原始业务数组顺序分配输入1起/输出2起/init0起；映射一经批准，新代码与新工程必须都消费同一份结果。此转换工具是迁移辅助，不是每次构建或运行的生成器。

若作者希望阈值为1、图像为2，而旧声明图像在前，则明确写映射 images→2、threshold→1，不能先自动编号后再人工只改声明。当前示例以新工具目标编号为准，不推断任何已安装工具的真实编号。

动态节点的端口来自旧节点配置，要为每个节点生成本地映射。表达式 variables 与 program 各自对应输入/输出，保持符号表；既有宿主静态参数占号后，动态编号从剩余高水位继续。复制节点保留其端口id，只重映射node/flow引用。

已缺失声明的工程无法从字符串可靠还原端口号。保持原文件，列出缺失工具及引用；等补齐旧声明/映射再转换。不要据当前排序猜号、丢端口后继续显示“转换成功”。迁移输出应附简短摘要：工具数、节点数、成功/未转换项、原文件位置；无需全量哈希链或历史数据库。

## 发布步骤

1. 固定要迁移的三仓开发基线和编号表，先合并 Contracts main 的新接口。
2. 两产品更新同一 Contracts 子模块提交，完成工具/宿主全部调用改造；native、Python、自定义模板和helpers一起切换。
3. 生成 schema6 声明、format7 示例工程和新夹具，执行定向编解码、SDK、桥接、动态节点测试。
4. 创建独立候选安装目录，用户持久工具根不清空；旧自定义资产转换到新根，验证完成后再切配置。
5. 真实安装创建函数/类、手动输入/上层绑定、排序、执行、重启、删除；测试带外部owner的刷新/关闭。
6. 一次全CPU候选回归；GPU按选定依赖profile单独执行，报告实跑和跳过。
7. 保留旧安装/原项目用于回退；不用新程序写回旧格式，也不让旧模块以同ABI号混进新包。

不要求提交全部仓库代码到一个仓库，也不把 Contracts main 改成普通复制目录；继续子模块工作流。
