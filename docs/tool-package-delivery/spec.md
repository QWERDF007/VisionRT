# 工具包交付与 Python 互操作规格

状态：已确认（2026-10-19）。本文是行为、契约和验收要求的唯一规格；验证结论见[验收报告](../VisionRT-VisionTools-验收评估报告.md)。

## Problem Statement

工具库与宿主需要独立开发、编译和交付。用户希望工具库按领域输出普通 DLL，再由打包脚本交付 ZIP 与元数据；宿主正常输出 EXE/DLL，部署时消费工具 ZIP，而不是依赖工具库源码或维护另一份工具清单。

现有目录扫描、索引与声明读取、宿主平台节点绑定需要收敛成同一条消费路径。C++/Python 转换应复用既有成果并集中维护，不能因为追求零拷贝而引入悬垂内存、重复转换规则或失控的 Python 对象生命周期。

## Solution

工具库编译领域 DLL，显式打包时收集构建产物、声明和必要资源，输出一个 ZIP 与同源索引。宿主构建不消费 ZIP，部署脚本才解包、调用 SDK 校验并安装工具包。运行中的宿主从安装包元数据得到工具列表和实现位置，执行 C++、Python 或已有平台能力。

工具包交付协议与计算后端无关，不预设 CPU/GPU 包类型或固定工具组合；依赖与资源按实际构建产物和声明收集，具体边界见 D-01、D-02 和 D-05。

继续使用现有 CMake、Python 打包脚本、标准库 zipfile、SDK 校验器与 pybind11，不另建更新框架。通用转换成为 SDK 可选支持，解释器与实例生命周期仍由宿主管理。必要更新在退出宿主后进行，不实现热替换。

## User Stories

1. **US-01**：作为工具库开发者，我希望普通构建输出领域 DLL，以便直接调试而不必先打包。
2. **US-02**：作为宿主开发者，我希望普通构建输出 EXE/DLL，以便不依赖工具库源码、ZIP 或安装结果。
3. **US-03**：作为算子作者，我希望多个同领域工具共享 DLL，以便避免每工具一个 DLL 的部署碎片。
4. **US-04**：作为维护者，我希望仅在实际职责或依赖需要时增加领域库，以便不维护空模块。
5. **US-05**：作为算子作者，我希望只维护一份工具声明，以便名称、分类、端口和默认值不会在宿主分叉。
6. **US-06**：作为算子作者，我希望工具身份独立于 C++ 工厂名称，以便实现重组不改变工程中的工具身份。
7. **US-07**：作为工具库维护者，我希望从既有构建清单收集真实 DLL 和依赖，以便不再手写产物定位规则。
8. **US-08**：作为发布者，我希望显式打包得到一个 ZIP 和配套索引，以便离线传递给部署人员。
9. **US-09**：作为发布者，我希望包内与包外索引完全一致，以便不用维护两套发布元数据。
10. **US-10**：作为发布者，我希望 ZIP 仅包含所选工具需要的库、声明、脚本和资源，以便不携带无关开发环境和数据。
11. **US-11**：作为工具库维护者，我希望同一交付协议适用于不同计算后端及其组合，以便不因后端差异另建打包或加载流程。
12. **US-12**：作为部署人员，我希望包携带所选工具的必要依赖和资源，并明确必须由目标环境提供的前提，以便不依靠开发机环境才能运行。
13. **US-13**：作为 Python 工具作者，我希望脚本与相对导入、相邻资源一并交付，以便部署后不依赖源码目录。
14. **US-14**：作为 Python 工具作者，我希望使用真实 Python 入口而非伪 DLL 项，以便工具发现符合实际实现方式。
15. **US-15**：作为部署人员，我希望宿主部署脚本直接接收工具 ZIP，以便不先手工解包或配置工具源码路径。
16. **US-16**：作为部署人员，我希望部署调用同一个 SDK 校验规则，以便生产者与消费者不会对有效包得出不同结论。
17. **US-17**：作为部署人员，我希望无效 ZIP、缺文件或冲突声明被明确拒绝，以便不破坏可用安装。
18. **US-18**：作为部署人员，我希望退出宿主后能更换完整工具包，以便不依赖运行中 DLL 的热覆盖。
19. **US-19**：作为工作台用户，我希望名称、分类、参数和端口随安装包变化，以便新增工具不要求重编译宿主。
20. **US-20**：作为工作台用户，我希望未列入索引的文件不会成为工具，以便工具列表可预测。
21. **US-21**：作为工作台用户，我希望未安装工具包时仍能打开工作台并看到明确的空工具状态，以便区分未安装与加载故障。
22. **US-22**：作为工作台用户，我希望平台接收节点的可见声明也来自工具包，以便平台节点没有另一份固定工具清单。
23. **US-23**：作为工程使用者，我希望更换包后缺失或不可执行的工具保留明确诊断，以便不会静默换成其他实现。
24. **US-24**：作为集成者，我希望在没有源码目录和开发 PATH 补偿的环境消费交付物，以便证明部署真实完整。
25. **US-25**：作为 SDK 消费者，我希望只使用核心 SDK 时无需安装 Python，以便保留纯 C++ 集成能力。
26. **US-26**：作为宿主维护者，我希望复用 SDK 中唯一的 Python 转换实现，以便 dtype、shape、stride 和 ROI 规则不重复维护。
27. **US-27**：作为算法作者，我希望 C++ 图像和数值输入以只读视图进入 NumPy，以便避免无意义复制且不允许通过该视图改写上游结果。
28. **US-28**：作为算法作者，我希望 ROI 等非连续图像使用真实步长，以便裁剪后数据不会错行或错通道。
29. **US-29**：作为 C++ 结果消费者，我希望返回数据不依赖已经释放的 Python 数组，以便后续节点和快照可正常使用结果。
30. **US-30**：作为算法作者，我希望错误 dtype、rank 或不支持的布局明确报错，以便不被隐式转换掩盖。
31. **US-31**：作为 Python 工具作者，我希望模型实例可跨执行复用，以便不在每次运行时重建模型。
32. **US-32**：作为宿主维护者，我希望停止、刷新和退出按正确顺序释放 Python 引用，以便没有 GIL 和解释器销毁顺序错误。
33. **US-33**：作为发布维护者，我希望没有源码中的历史格式兜底或第二套打包入口，以便长期只维护一条交付路径。
34. **US-34**：作为项目负责人，我希望只实现当前需要的校验和更新行为，以便不引入哈希、签名、差分升级或通用插件平台。
35. **US-35**：作为工具作者，我希望声明直接使用工具名称作为文件名、工具 DLL 使用简短领域名，以便目录、文件名和身份不重复表达。
36. **US-36**：作为流程作者，我希望只添加一个跨流程接收工具，输出类型随所选源端口确定，以便不必从多个类型变体中选择。

## Implementation Decisions

### D-01：分离构建与交付

- 两仓普通构建分别输出 DLL、EXE/DLL，不隐式压缩、安装工具或触发应用部署。
- 保留显式打包操作。工具库输出 ZIP 和外置索引，宿主打包部署操作输入 ZIP；不要求额外常驻安装服务。
- 打包、校验、部署和发现不按 CPU/GPU 或其他计算后端分叉，不强制分包或固定工具组合；是否划分发行变体由实际构建与交付需要决定，不新增后端管理框架。
- 复用现有脚本和标准库 zipfile，不采用第二套打包框架、原生 ZIP 解析链或完整应用更新框架。

### D-02：领域库与声明来源

- VisionTools 作者声明使用 `工具名称.yaml`，同目录内不重名；工具身份仍由 tool_id 唯一确定，不从文件名生成，也不因文件改名改变。
- 自有工具 DLL 使用 `vst_<领域>.dll`，实际输出名以领域目标的 CMake 配置为准。第三方库不改名，通用包读取协议不要求特定厂商或文件名前缀。
- 复用现有领域库，按真实职责和依赖组织多个工具；领域种类不构成工具包类型白名单，不按每个类或每份声明自动生成 DLL。
- 工具声明是名称、分类、端口、默认值和脚本入口的作者源；实现绑定描述领域归属，CMake 目标决定实际产物。
- 只有不能从既有声明和构建清单确定的必要资源才增加显式资源项，不扫描整个开发环境推测资源。
- 必要资源可包含工具运行所需的模型、配置及其他数据；不预设模型必须排除或全部纳入，按所选工具的实际资源声明收集。

### D-03：统一包读取 Interface

- SDK 提供一次读取并校验工具包、返回强类型工具包描述的 Interface；描述关联最终索引、解析后的工具声明和实现位置。
- 校验 CLI、宿主部署和运行时复用该语义。已有仅校验入口委托同一读取逻辑，不新增一套 Python 端口校验器。
- 临时解包、ZIP 写入和目标目录操作仍在脚本中；SDK 核心不因此依赖 ZIP 或 Qt。
- 先在现有有效工具包和真实宿主消费路径贯通该 Interface，再修改发布格式；验收样例不成为包内容或计算后端限制，不先拆出只有单一调用价值的空抽象。

### D-04：最终索引与工具身份

- 继续使用协议文件名 `module_index.yaml`，发布格式显式升级为 schema version 2，不接受自动探测旧格式。
- 保留发行变体、领域模块、工具及运行文件的信息；变体仅描述实际发行配置，不枚举或据此限制计算后端和工具组合。包版本派生自工程版本，不维护第二处版本号。
- 工具以 `tool_id` 为稳定身份；声明中的身份必须与索引一致。C++ 的 `registry_name` 仅供实现工厂定位。
- 每个工具项引用唯一声明。C++ 领域工具引用模块，Python 工具由声明定位脚本；Python 项不需要模块，也不能伪造 DLL。
- 分类是声明的显式属性，不从目录名推断；安装包声明在宿主中只读，作者修改通过工具库重新打包交付。
- 对已有宿主能力，工具项使用 `host_binding` 指明执行器绑定。它与领域模块引用互斥，不能用于 Python 工具；不是新增通用能力发现或权限框架。
- 只有 Python 或宿主能力的包允许模块集合为空。未引用模块、重复工具身份和错误实现组合必须拒绝。
- 包内引用均相对于安装包解析；缺声明、脚本、模块或必要资源必须失败，不能回退到源码目录。

### D-05：ZIP 与配套元数据

- 最终 ZIP 根部包含协议索引及其引用的声明、库、脚本和必要资源；不嵌套开发机绝对目录。
- 从所选构建产物及声明收集实际需要的依赖和资源，不因后端名称增删文件；必须由目标环境提供的硬件、驱动或运行环境前提应明确，不将开发机隐式依赖视为已交付。
- 非代码资源由声明显式列出，路径相对于声明目录；不收集缓存、开发样例目录或无关文件。
- 外置索引是包内最终索引的逐字节副本。它用于查看工具身份和引用，完整显示信息仍从被引用声明读取。
- 临时收集目录通过 SDK 校验后才压缩和发布；发布产物不携带另一套独立编辑的声明摘要。
- 构建中间索引不视为可安装包，必须在真实产物路径填充并校验后交付。

### D-06：宿主部署 Interface

- 部署入口使用 `--tools-package` 接收 ZIP，取代面向外部已解包目录的入口；可选外置索引只用于一致性检查，不替代包内内容。
- 先在临时目录完成解包与 SDK 校验，再写入唯一的安装工具目录；禁止绝对路径、父目录逃逸及通过链接逃逸的条目。
- 结构校验与真实加载不同：库文件存在不等于传递依赖完整，发布验收必须实际装载和执行。
- 拒绝无效输入时不删除或改写既有有效安装。正常目录操作失败必须明确失败，不标记安装成功。

### D-07：目录驱动工作台

- 运行时只按安装包索引引用读取声明并生成列表，不额外扫描旧内置目录或猜测候选根目录。
- 元数据读取与展示不提前执行 Python 算法或初始化模型；执行时才走对应实现。
- 新增、删除、重分类工具均由包决定，宿主不维护工具 ID、名称、端口或类型后缀清单。
- 无包时允许启动空工作台；包损坏或实现不可用必须有诊断，不回退到另一份算法声明。
- 沿用现有工程缺失工具诊断，不借此扩展自动迁移或工具替代系统。

### D-08：宿主平台节点

- 跨流程接收只发布一个声明和一个工具身份，不按数据类型展开，也不在宿主隐藏注册类型变体。
- 其数据输出通过 SDK 的声明式类型引用确定类型；所引用的流程、节点和端口由初始化参数选择，完整 TypeSpec 来自源节点的有效输出，包括 dtype、rank、layout。
- 编辑、复制、保存重开与执行使用同一节点类型解析实现。未绑定、引用失效或引用循环的输出没有具体类型，执行前明确失败；不使用 Any、默认整数类型或隐式转换绕过。
- 源端口类型变化必须重新检查下游连接，不能静默保留不兼容连线的可执行状态。声明和具体属性格式以 [SDK Schema](../../3rdparty/VisionRTSDK/include/visionrt/sdk/Schema.h) 及工具库作者声明为准。
- 流程调度和结果读取仍由宿主实现；其可见节点声明归工具包所有。
- 保留一个按绑定标识选择执行器的内部入口；执行器接收解析后的声明，从声明获得输出类型，不枚举具体工具 ID 或后缀。
- `host_binding` 的存在性由宿主解析；未知绑定使该工具实现不可用并报错，不能偷偷注册默认实现。
- 不新增宿主能力 DLL、网络能力注册、服务定位框架或跨进程执行协议。

### D-09：完整包更换

- 更新采用退出宿主、更换完整工具包、重新启动的顺序。发现文件被占用时明确失败，不强杀用户进程。
- 更换后旧包独有的工具、脚本和依赖不残留；继续按索引生成列表并诊断既有工程缺失工具。
- 仅保证输入校验失败不破坏现有安装，以及实际文件操作失败不会被报告成功；不承诺断电事务恢复或任意时点回滚。

### D-10：SDK 可选 Python 支持

- `VisionRT::ToolSDK` 保持纯 C++；`VisionRT::PythonInterop` 是可选目标，不引入宿主 UI、调度器或指标模型依赖。
- 迁移现有通用转换，保留小 Interface `toPythonReadonly` / `fromPython`，移除宿主重复实现；不同时维护新旧转换器。
- 解释器、导入、工具对象和刷新仍归宿主 PythonRuntime；工具 DLL 和 SDK 不创建各自的解释器单例。

### D-11：数据所有权与布局

- C++ 节点之间沿用 SDK 只读共享存储。图像和数值输入使用正确 dtype、shape、真实 strides 及持纯 C++ owner 的 capsule base。
- NumPy 输入视图标记只读；这不是对所有可写别名的强制隔离，不承诺阻止任意原生扩展改写底层内存。
- Python 输出默认复制到纯 C++ 所有者。图像按真实步长复制；数值数组维持明确的连续性要求，不通过隐式 forcecast 改变 dtype 或布局。
- 返回后 C++ 结果不得依赖 Python owner；字符串和复杂结果使用显式转换，不承诺所有数据零拷贝。
- QuickTools 只作为代码经验来源，不直接复用无 base 的复制构造、无 owner 的裸 Mat 或忽略 strides 的反向包装。

### D-12：对象与 GIL

- 保持一个主解释器；全部工作任务和工具实例必须在其销毁前结束。
- Python 引用的获取、使用、缓存清理和析构必须满足解释器及 GIL 规则；不得把 Python 引用放入纯 C++ 值、结果快照或任意线程析构的 owner。
- 模型实例和可调用对象可跨执行缓存，停止、刷新、退出在正确生命周期边界清理；等待需要 GIL 的工作任务时不能占着 GIL。
- `.release()` 转移引用所有权，不作为销毁 Python 对象的替代；纯 Python 刷新不等于原生扩展热卸载。

### D-13：受控 ABI 与跨仓收敛

- 沿用统一 SDK、兼容编译工具链及运行库的受控 C++ ABI；现有 C 导出符号不意味着所有 STL 和虚接口可跨任意编译器使用。
- 保留已有 ABI 主版本检查，不新增 ABI 指纹或通用兼容探测系统。
- 格式变更在同一切片内同步更新 SDK、生产者、消费者和相关子模块锁定版本；交付时不保留旧参数兜底或双格式分支。
- 删除已被替代的声明扫描、打包和转换路径，测试夹具不能变成生产工具源。

## Testing Decisions

### 主要测试 Seam

首选“真实工具包经部署入口安装后，工作台列出并运行其中工具”的高层 Seam。它覆盖元数据、SDK、脚本、动态库、Python 与运行时，而不为每层新建模拟入口。

通用转换另复用现有 PythonRuntime 工具执行 Seam 验证，SDK 独立消费者验证可选依赖，不新增专为测试暴露的内存管理 Interface。

### 良好测试的标准

- 断言用户可见列表、实际数值结果、错误和所有权行为，不断言内部 Helper、调用顺序或目录猜测分支。
- 使用真实 SDK 校验器、领域 DLL、Python/NumPy、文件系统和下一层依赖；不得用相邻层 mock 伪造部署成功。
- 内存行为用存储地址、步长、可写性和释放后结果验证；不以“没有抛异常”代替正确性，也不无证据声称更快。
- 局部 red-green 验证先于实现；每片完成做真实资源消费验证，全部实现收口后才做必要的整体回归。

## Out of Scope

- SHA256、签名、元数据加密、差分包、云更新、插件市场、通用安装框架。
- 运行中 DLL/PYD 热替换、进程强杀、断电事务恢复、任意时点回滚。
- 为所有工具单独建 DLL、预建空领域库、强制按计算后端分包、打包无关模型或完整开发环境、部署时在线安装 Python 依赖。
- 任意 NumPy 输出零拷贝托管、Python owner 异步回收队列、共享输出 allocator、DLPack、nanobind 迁移、多解释器或 free-threading 改造。
- 纯 C ABI 重构、跨编译器兼容平台、额外兼容旧元数据和旧部署入口、重写 QuickTools。
- 与包列表及参数呈现无关的 UI 改版，新增算法，工程自动迁移或工具替代。
