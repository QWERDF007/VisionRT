## 3. F-E01：Ready 后部分业务入口重新开放（P2）

**触发条件：** 关闭已经完成至 `ClosePhase::Ready`，但 AppController 尚未销毁；例如同步 closeReady/closingChanged 槽重入，测试宿主持有控制器，或窗口关闭后对象延迟销毁。不是声称普通用户每次关闭都能点击到该窗口。

**代码链：** Ready 转换把 `closing` 设回 false、`pending` 清空。`isClosing()` 仍因 phase 返回 true，但 `Impl::idle()` 只检查 closing 和 runtime/pending；`start()`、编辑 command、refreshPython 依赖这个旧判断。`poll()` 在 Ready 直接返回。故允许的新任务可能不再被正常消费，且会尝试在 Python 已 prepareShutdown 后重新发起工作。

**证据：** [idle](https://github.com/QWERDF007/VisionRT/blob/6df386eeafe208a5ade6fa382a253611482717ab/src/ui/AppController.cpp#L266)、[Ready 和 poll 早退](https://github.com/QWERDF007/VisionRT/blob/6df386eeafe208a5ade6fa382a253611482717ab/src/ui/AppController.cpp#L395)、[start](https://github.com/QWERDF007/VisionRT/blob/6df386eeafe208a5ade6fa382a253611482717ab/src/ui/AppController.cpp#L582)、[关闭尾部](https://github.com/QWERDF007/VisionRT/blob/6df386eeafe208a5ade6fa382a253611482717ab/src/ui/AppController.cpp#L804)、[isClosing](https://github.com/QWERDF007/VisionRT/blob/6df386eeafe208a5ade6fa382a253611482717ab/src/ui/AppController.cpp#L1450)。

**修复：** 用一个内部 `isClosing()`/`closingInProgress()` 谓词覆盖 Resetting、AwaitOwners、Ready；idle、start、refresh、编辑、保存、读回统一消费。优先保留现有状态机，仅去掉布尔和枚举的判断分歧。Ready 是终态，不因窗口不可见或 closing 布尔归零而重新接单。QML 的运行/刷新等按钮也应检查 closing，后端仍是最后防线。

**验证：** closeReady 同步槽尝试 runOnce、refreshPython、一次编辑；构造/初始化计数不增长，无新管理任务，结果只触发一次。补无外部 owner 和 AwaitOwners 两条 Ready 路径。保留未保存弹窗正常保存用例。

**证据级别：源码确认；未运行 Qt 重入复现。** 对 T-D01 已修复的 save/synchronize 不重新判失败。

## 4. F-E02：菜单可连接，但提交拒绝（P2）

**触发：** A 在上层、B 在下层。B 的普通整数输入曾关联 A，随后切为 Literal 手动输入；`setMode()` 保留旧 source 作为草稿。打开一个合法上层输出的名称级联菜单。

**实际链路：** `candidateInputsWithState()` 只把 Upstream 的 source 判为 connected/occupied，因此该目标显示可点；QML 点击调用 bindOutputTo→bindFreeInput，后者以任何 `binding.source` 为已占用，抛出“输入端口已关联上游”。旧 `compatibleInputs()` 也直接过滤任何 source，但当前名称菜单走的是前一套候选函数。因此准确现象是**显示可连接而点击失败**，不是当前名称菜单必然隐藏。

**证据：** [候选状态](https://github.com/QWERDF007/VisionRT/blob/6df386eeafe208a5ade6fa382a253611482717ab/src/core/ProjectEditor.cpp#L398)、[提交入口](https://github.com/QWERDF007/VisionRT/blob/6df386eeafe208a5ade6fa382a253611482717ab/src/core/ProjectEditor.cpp#L547)、[切模式保留 source](https://github.com/QWERDF007/VisionRT/blob/6df386eeafe208a5ade6fa382a253611482717ab/src/core/ProjectEditor.cpp#L607)、[当前 QML 点击](https://github.com/QWERDF007/VisionRT/blob/6df386eeafe208a5ade6fa382a253611482717ab/src/ui/qml/OutputPanel.qml#L248)。

**修复：** 统一“有效绑定”为 `mode == Upstream && source`。用同一个小型状态判断提供 Free/ConnectedHere/Occupied；Literal 的旧 source 不占用有效输入。用户明确点击新连接后可更新该草稿并切为 Upstream；其他活动来源仍不可静默覆盖。候选、兼容查询和提交保持一致，继续调用 validateBinding 校验严格向下、类型和端口。不要清空整个工程的闲置 source，也不要改写 JSON 模式。

**验证：** Literal+同来源草稿、Literal+其他来源草稿均能连接；Upstream+其他来源仍禁止；已连当前输出勾选/解绑不变；同级/向上/自身、错误类型仍拒绝；切换手动后保存重开重复该用例。

**证据级别：源码调用链确认；未运行 Qt GUI。**

## 5. F-E03：YOLO 填充区框占名额并抑制有效框（P2）

`YoloPostprocess.cpp` 先按网络坐标筛选、排序、NMS、达到 maximum 即停止，最后 inverse 到原图并删除零面积框。完全落在 letterbox padding 的高分框在被删除前，已影响 maximum 和 NMS。

**本次直接编译仓库实际后处理实现，独立复现两例：**

```text
disjoint maximum=1 -> 0; maximum=10 -> 1
padding suppression maximum=10 -> 0; without padding candidate -> 1
REPRODUCED: padding candidates consume limit and suppress valid image boxes
```

使用 32×32 网络、stride=8 的 4×4 输出头；原图映射占 y=[8,24]。高分框 [0,0,8,8] 完全在 padding；另一个低分框与原图有交集。两例分别隔离名额占用和无效框抑制。probe 调用的是产品源码函数，没有重写后处理算法，也不依赖 GPU/模型权重。

**证据：** [筛选至最后裁剪](https://github.com/QWERDF007/VisionTools/blob/aa92f9e578b7780b85fde71d4aee25cf88182f2d/src/infer/YoloPostprocess.cpp#L59)；`evidence/yolo_padding_probe.cpp` 与实际输出。

**最小修复：** 在加入 selected、参与 NMS 和计数前，利用实际 letterbox 几何确认映射裁剪后的框有正面积；否则仅保留可选 trace，不能进入有效候选。保留现有网络坐标 IoU、类别隔离、稳定排序和阈值规则。这样无需更改所有有效框的 NMS 语义。若将来改为原图裁剪框做 IoU，属于独立算法变更，需单独对比参考结果。

单纯增大 max_detections 不能解决第二种抑制问题。不得在 VisionRT 中补救算法输出；修复归 VisionTools。
