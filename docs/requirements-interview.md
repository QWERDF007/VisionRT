# VisionRT 需求访谈记录

本文件记录 VisionRT 的产品需求访谈过程。问题会随着讨论持续补充，回答和结论用于约束后续产品设计与技术实现。

## 当前目标

构建一个类似工业视觉流程编排软件的 Windows 桌面应用，提供工具库、DAG 流程编辑器、运行结果展示区和工具参数配置区。

## 已确认约束

- 首版目标平台为 Windows 桌面软件。
- 暂不需要连接相机、串口或 PLC 等工业硬件。
- 深度学习工具会使用 GPU。
- 首版交互阶段可以先使用模拟数据，不要求立即真实执行 DAG。
- 最终运行时必须使用 [Taskflow](https://github.com/taskflow/taskflow) 实现流程 DAG。
- 最终产品需要真实执行完整项目流程，而不是只展示流程图或模拟节点状态。

## 访谈问题与回答

### 1. 首版交付形态与运行环境

**问题**

你希望首版交付 Windows 桌面软件、浏览器 Web 应用，还是先做可交互原型再决定技术形态？是否必须离线运行，以及是否需要直接连接相机、串口、PLC 或本地 GPU？

**回答**

桌面软件，暂时不需要连接相机、串口、PLC，但是会用到 GPU，例如深度学习工具。

**结论**

首版按 Windows 桌面应用规划，暂不纳入工业硬件接入，但需要为本地 GPU 推理和深度学习工具预留运行时能力。

### 2. DAG 执行范围

**问题**

首版必须真实执行 DAG 吗？例如“加载图片 → 图像预处理 → 深度学习推理 → 后处理 → 结果展示”，还是先完成流程编排、参数配置和界面交互，工具执行暂时使用模拟数据？

**回答**

首版可以不用真实执行 DAG，但是最终交互需要使用 Taskflow 完成流程 DAG，并且需要真实执行完整项目流程。

**结论**

首版可以优先完成流程编辑器和交互验证，但节点、端口、参数、数据传递和项目序列化不能设计成只适用于演示的临时模型，后续必须能够落到 Taskflow 的真实执行模型上。

### 3. 工具扩展方式

**问题**

工具库中的工具是否需要允许第三方或用户自行扩展？如果需要，工具主要以固定内置模块提供，还是需要设计 C++ 动态库、Python 脚本或两者兼容的插件机制？

**回答**

内置一些固定的 C++ 工具和 Python 工具，并且支持用户自行扩展 Python 工具。

**结论**

工具系统需要同时容纳内置 C++ 工具、内置 Python 工具和用户自定义 Python 工具。Python 工具需要有稳定、可文档化的输入输出契约，并需要继续确认其运行环境、依赖管理和异常处理方式。

### 4. 首个端到端验收流程

**问题**

请定义首个必须真实执行的端到端示例，包括输入、节点链路和最终输出。

**回答**

本地图片 → 按投影提取 ROI → 图像裁剪 → 图像预处理 → YOLO C++/Python 推理 → 后处理 → 结果展示。

**结论**

首版需要围绕图像流设计一条可真实运行的样例流程，至少覆盖原图、ROI 或裁剪图、预处理图、检测结果和可视化结果等阶段。投影提取 ROI 的具体算法参数，以及 YOLO 的 C++/Python 实现方式和模型后端仍需进一步确认。

### 5. YOLO 首版实现后端

**问题**

“YOLO C++/Python 推理”是同时提供两种实现，还是同一工具的两种可选后端，或者首版先实现其中一种？

**回答**

首版先实现 C++，具体使用 [InferRT](https://github.com/QWERDF007/InferRT/tree/dev) 的 `dev` 分支。

**结论**

首版 YOLO 节点先采用 C++ 实现，InferRT 作为具体推理实现。Python YOLO 后端不纳入首版验收，但工具系统仍需保留 Python 内置工具和用户扩展 Python 工具的能力。

### 6. YOLO 模型交付格式

**问题**

首版的 YOLO 工具需要加载哪一种模型产物作为项目运行输入：ONNX 模型、TensorRT engine，还是其他 InferRT 专用格式？是否需要在软件内提供模型转换或构建 engine 的能力？

**回答**

首版支持加载已经构建好的 TensorRT engine，也支持由 InferRT 在运行时构建。

**结论**

YOLO 节点需要同时兼容两种模型准备路径：直接加载 engine，以及从上游模型在运行时构建 engine。项目配置需要能够记录模型路径、模型类型和构建或加载所需的参数，并明确模型与 GPU/TensorRT 环境的兼容性。

### 7. 首版 GPU 运行环境

**问题**

首版验收是否固定一套 NVIDIA GPU、CUDA 和 TensorRT 环境？如果固定，请给出 GPU 型号以及 CUDA、TensorRT 版本；如果不固定，请说明首版需要覆盖的环境范围。

**回答**

首版支持一套可控的 Windows + NVIDIA 环境。

**结论**

首版先以单一、可控的 Windows + NVIDIA 环境作为验收基线。具体 GPU、CUDA 和 TensorRT 版本需要在 InferRT 集成阶段进一步锁定，暂不承诺跨环境兼容。

### 8. 项目文件的可移植性

**问题**

项目保存时，项目文件需要保存到什么程度？是只保存 DAG 和工具参数，还是还要保存模型、图片、Python 脚本等资源的引用，或者打包成包含这些资源的完整项目包？

**回答**

在本机保存时，只保存 DAG、节点参数和外部资源路径。外部资源路径包括图像路径、模型路径等，Python 脚本引用不需要写入项目文件，因为脚本位于软件固定目录，例如 `<软件>/tools/python`。跨机器打开属于单独的“导出”功能，由导出功能负责处理资源迁移。

**结论**

项目保存和项目导出是两个不同的能力：保存生成本机引用型项目文件，导出生成可迁移项目包。项目文件不负责复制 Python 工具脚本，但导出方案仍需明确软件内置工具目录和跨机器资源的打包规则。

### 9. 流程图拓扑能力

**问题**

首版流程是否严格保持无环 DAG，并支持哪些拓扑：仅线性连接，还是还要支持一对多分支、多对一汇合、条件分支和并行执行？

**状态**

**回答**

首版支持线性、分支、汇合和并行执行，不支持条件路由，并且严格禁止环。

**结论**

首版流程编辑器和运行时需要支持线性连接、一对多分支、多对一汇合以及可并行执行的独立分支。连线操作和项目加载时都必须进行环检测，任何有向环都应被拒绝。条件路由暂不纳入首版。

**术语说明**

- **线性**：一个节点完成后只进入下一个节点，例如 `加载图片 → ROI 提取 → 裁剪 → 预处理 → 推理`。
- **分支**：一个节点的结果同时交给多个后续节点，例如预处理结果同时进入推理和图像统计。
- **汇合**：多个上游节点都完成后，结果共同进入一个下游节点，例如原图和检测结果共同进入结果绘制。
- **条件**：运行时根据数据或节点结果选择不同路径，例如检测到 ROI 时进入裁剪，未检测到 ROI 时进入异常处理。
- **并行执行**：多个互不依赖的节点或分支同时运行，例如多个 ROI 分别进行推理，最后再汇合结果。
- **环**：流程连线最终回到之前的节点，例如 `A → B → A`。严格 DAG 不允许环；需要重复处理时，应另行设计有界循环或重试机制。

上述能力可以组合使用。比如条件节点选择是否继续处理，选择出的多个 ROI 再并行推理，最后汇合为统一结果。

### 10. 节点数据类型与端口契约

**问题**

节点之间的输入输出端口是否需要强类型校验？首版节点之间至少需要传递哪些数据类型，例如图像、ROI、检测结果、标量、字符串或列表？

**回答**

需要强类型校验。每个工具定义自己的输入参数和输出参数，节点之间严格按照参数类型校验，不同类型的数据不能连接。首版需要支持：图像、ROI 区域、标量或字符串组成的多维数组，以及检测结果相关数据。ROI 区域包括矩形、多边形、点集、圆等。检测结果通常包含多个字段，例如图像、矩形或多边形等 ROI、一维置信度数组、类别数组和类别名称字符串数组。

**结论**

节点端口必须具备明确的数据类型和连接兼容性规则。数据模型需要同时支持基础类型、数组类型、几何 ROI 类型和包含多个字段的检测结果类型；不能用无约束的通用对象替代类型校验。

### 11. 复合检测结果的端口形式

**问题**

检测结果中的图像、ROI、置信度、类别和类别名称等字段，应该作为一个整体的 `DetectionResult` 复合类型从节点输出，还是拆成多个强类型输出端口分别连接？

**回答**

检测结果拆成多个强类型输出端口。

**结论**

YOLO 节点以及其他检测类工具应分别暴露图像、ROI、置信度、类别和类别名称等强类型输出端口。下游节点可以只连接所需字段，编辑器和运行时对每条连线分别进行类型校验。

### 12. 数组长度与空结果

**问题**

标量、类别、置信度和检测结果数组是否需要支持运行时动态长度，例如一张图检测到 0 到 N 个目标？空数组和不同长度的数组是否都属于合法结果？

**回答**

允许空数组。置信度、类别、类别名称和 ROI 数组是多维数组，其中一个维度对应检测目标数量 `N`，并支持批量图片的多维数组。

**结论**

检测结果必须支持动态数量的目标集合，包括 `N = 0` 的空结果。检测字段需要保留多维数组的形状信息，并支持批量维度；同一检测结果中的 ROI、置信度、类别和类别名称必须按照相同的批量维和目标维保持对应关系。

### 13. 多维数组的形状约定

**问题**

多维数组是否需要统一的维度顺序和形状约定？例如统一使用 `[批量数 B, 目标数 N, ...]`，并要求连接时校验数组元素类型、维度和对应维度的关系；还是允许不同工具使用不同的维度顺序，只要元素类型相同即可连接？

**回答**

按照 `[B, N, ...]` 的维度约定。连线时根据工具声明的输入参数进行校验，例如输入需要二维数组时，上游输出必须是二维数组才能连接。

**结论**

首版使用统一的 `[B, N, ...]` 维度语义。节点端口声明数据类型和数组维度，编辑器在连线时按下游输入要求校验，上游输出不满足类型或维度要求时禁止连接。更细的形状兼容规则和变长 ROI 点集表示仍需在数据类型设计阶段确定。

### 14. Python 工具的类型声明方式

**问题**

用户自定义 Python 工具如何声明输入、输出和参数类型？可以采用 Python 固定接口、装饰器或基类、独立元数据文件，还是由软件界面创建工具定义后绑定 Python 脚本？

**回答**

用户创建 Python 脚本并放到固定目录，例如 `<软件>/tools/custom`。Python 工具支持脚本中的函数和类：软件界面创建工具定义时，指定脚本文件以及要调用的函数，或者指定脚本文件以及要使用的类。类工具必须实现约定的固定方法。工具定义保存为 YAML 元数据文件。

内置 Python 工具和用户自定义 Python 工具使用同一套工具定义和调用方式。

内置 C++ 函数式工具在代码中完成接口注册，界面创建工具时指定要调用的函数接口，实际运行时通过注册表查询对应接口。内置 C++ 类工具也在代码中注册，并且必须继承固定基类。

**结论**

工具系统需要统一管理四类工具来源：内置 Python 函数、用户 Python 函数或类、内置 C++ 函数、内置 C++ 基类工具。工具元数据负责描述名称、输入输出和参数，并记录 Python 文件与函数/类，或 C++ 注册接口标识；运行时通过对应注册表或 Python 加载器解析实现。

### 15. 工具实例生命周期与并发

**问题**

对于需要继承固定基类的类工具，实例应如何管理：每个流程节点创建一个独立实例，初始化一次后可执行多次，还是每次执行都创建新实例？在并行执行时，是否允许多个任务共享同一个工具实例？

**回答**

每个流程节点创建一个独立实例，初始化一次，执行期间复用；同一实例不允许并发调用。

**结论**

节点实例与流程节点一一对应。实例可以在初始化阶段加载模型或创建运行资源，在流程执行阶段重复使用；Taskflow 的并行任务不能同时调用同一个实例，但不同节点实例可以并行执行。C++ 和 Python 类工具需要遵循一致的实例生命周期语义。

### 16. 类工具固定方法

**问题**

类工具需要实现哪些固定方法，以及每个方法的职责是什么？例如初始化、单次执行、重置、停止和释放资源。初始化是否接收节点参数，执行是否只接收强类型输入并返回强类型输出？

**回答**

类工具必须实现 `initialize`、`execute` 和 `release` 方法。工具不需要 `stop` 接口；系统执行停止时等待当前流程中的工具完成。每个方法都返回状态码和状态信息，状态码、状态信息是每个工具的两个固定输出。

**结论**

C++ 类工具和 Python 类工具需要共享同一套生命周期语义：初始化、执行和释放。工具执行结果除业务数据外，还固定产生状态码和状态信息。系统停止不调用工具级 `stop`，而是等待当前工具调用完成后结束流程。

### 17. 状态输出的连接方式

**问题**

状态码和状态信息作为每个工具的固定输出后，是否允许普通工具连接并消费它们？还是由运行时统一采集，用于运行状态面板、日志和流程级错误汇总，不参与普通业务数据连线？

**回答**

状态码和状态信息作为普通强类型输出，允许下游工具连接和处理。状态码是整型输出，状态信息是字符串输出；下游工具声明对应的整型或字符串输入时即可连接。

**结论**

状态码和状态信息既由运行时统一采集，也属于可参与 DAG 连线的业务数据。工具端口模型需要把这两个固定输出与其他强类型输出一样纳入连接校验。

### 18. 工具错误后的流程策略

**问题**

当某个工具返回错误状态码时，流程应该如何处理：立即停止整个流程，继续执行下游并让下游工具处理错误状态，还是由项目或节点配置决定？

**回答**

工具发生错误时仍继续执行下游节点，让下游根据输入处理。错误工具的业务输出可能为空，下游工具遇到空数据也可能报错，最终整个 DAG 标记为报错。

**结论**

首版采用错误继续传播策略，不因单个工具错误自动短路 DAG，也不生成流程级错误结果。每个工具节点自身保存并输出状态码和状态信息：成功时状态码为 `0`，错误时状态码为非 `0`；错误后的业务输出保留或清空由工具实现决定。下游节点可以同时读取上游状态码和业务输出，并自行决定如何处理空或异常输入。

### 19. 节点级状态与流程状态

**问题**

每个节点是否独立保存自己的状态码和状态信息，不在上层再汇总成一个 DAG 状态码？当节点报错时，只保留非零状态和状态信息，不产生正常业务输出；依赖该节点的下游通过状态码和输出自行调整处理。

**回答**

每个节点，即工具自身存储节点的状态码、状态信息，不用汇总。上层节点报错，则不应该正常输出，且状态码为非 `0`；下一级节点如果依赖上层节点，可根据上层节点的状态码以及输出调整处理。

**结论**

状态以节点为边界保存和传递，不设计额外的 DAG 级状态码汇总。流程运行器仍需记录节点运行状态以供界面展示，但不能用汇总状态替代节点自身的状态输出。

### 20. 多输入节点的调度条件

**问题**

对于有多个输入端口的汇合节点，Taskflow 何时调度它执行：所有输入端口都收到数据后执行，还是只要部分输入到达就执行？如果某个必需输入来自错误节点且没有正常业务输出，该汇合节点是否仍执行并接收该节点的非零状态码和空输出？

**回答**

所有输入端口都收到数据后执行。没有可选输入，只要完成接线就是必需输入。空输入和空输出也是一种有具体类型定义的数据，例如空数组 `[]`、空字符串 `""`。来自错误节点时，即使业务输出为空，汇合节点仍然执行，由汇合节点内部处理空输入以及上游状态。

**结论**

多输入节点必须等待所有已接线输入端口完成数据传递后再执行。空值不等于输入未到达，空数组、空字符串等必须作为已到达的合法数据参与调度。错误上游不能阻止下游执行，错误状态码和空业务输出都作为输入上下文传递给下游。

### 21. 并行执行粒度

**问题**

首版的并行执行是否只针对 DAG 中互不依赖的节点或分支，例如多个 ROI 推理节点同时运行；还是还需要让同一个节点对 `[B, ...]` 批量数据进行内部并行处理？节点实例本身仍然不允许并发调用。

**回答**

只并行执行 DAG 中互不依赖的节点或分支。单个节点对批量数据的处理由节点内部负责；同一个流程节点实例不并发调用。

**结论**

Taskflow 负责流程拓扑层面的并行调度，不拆分单个工具的批量输入。工具可以在自己的 `execute` 内部处理 `[B, ...]` 数据，但节点实例在一次或多次流程执行中都必须遵守不并发调用约束。

### 22. 流程运行控制

**问题**

首版流程运行是单次执行，还是支持连续运行/重复触发？顶部运行控制需要哪些操作：运行、停止、暂停、恢复、单步执行或重新运行？

**回答**

首版支持单次运行、停止、循环/连续运行和复位。复位的含义是重启软件，然后重新打开当前项目。

**结论**

顶部运行控制至少包括运行、停止、循环/连续运行和复位。复位不是清空节点状态，而是按当前项目重新启动应用并恢复项目。循环/连续运行的触发间隔、数据更新方式和停止条件仍需明确。

### 23. 循环/连续运行语义

**问题**

循环/连续运行如何重复执行流程：完成一次 DAG 后立即开始下一次，按固定时间间隔触发，还是由外部输入/用户手动触发？循环运行是否复用每个节点实例，还是每轮重新初始化？停止时需要等待当前轮完成，还是立即调用各工具的 `stop` 方法？

**回答**

每轮 DAG 完成后立即开始下一轮，复用已经初始化的节点实例。点击停止时等待当前轮完成，当前轮结束后停止继续循环。

**结论**

循环运行不重复初始化节点实例。运行器在每轮完成后立即重新调度 DAG；停止请求以当前轮结束为边界，不强制中断正在执行的节点。工具不提供 `stop()` 方法，系统等待当前工具调用完成后结束循环。输入数据在每轮之间如何更新仍需定义。

### 24. 连续运行的输入更新

**问题**

在本地图片作为输入时，连续运行每轮读取什么数据：重复读取同一张图片、按目录或文件列表顺序读取下一张图片、由输入节点内部产生或等待新数据，还是由用户在参数中选择模式？

**回答**

由输入工具参数选择，读图工具自行处理连续运行时的数据读取模式。

**结论**

流程运行器只负责按轮次调度 DAG，不定义输入数据的产生方式。读图工具需要通过自身参数支持连续运行所需的输入策略，例如重复读取同一文件、遍历文件列表或等待新数据；具体模式和参数名称由读图工具定义。

### 25. 参数编辑与校验时机

**问题**

右下角参数区修改节点参数后，参数何时校验：输入时即时校验、失去焦点时校验、保存项目时校验，还是点击运行前统一校验？参数错误时是否允许保存项目？

**回答**

UI 层限制输入范围，由参数定义时提供的范围控制；超过范围的值无法填写或修改。这样工具通常可以拿到合理数值；如果需要更严格的检查，再由工具层自行进行二次校验。

**结论**

参数定义需要包含可供 UI 使用的约束，至少覆盖数值范围。UI 应在编辑阶段阻止越界值进入节点配置，工具仍可在初始化或执行时进行自己的业务校验。其他参数约束（如枚举、必填、默认值和路径合法性）仍需明确。

### 26. 参数定义字段

**问题**

除了数值最小值和最大值，参数定义是否还需要支持数据类型、默认值、是否必填、枚举选项、步长、精度、字符串长度、文件/目录选择器和资源路径类型等字段？

**回答**

参数定义需要支持数据类型、默认值、步长和精度、文件/目录选择器，以及动态参数。例如设备选择参数可以根据运行环境提供 GPU、CPU 等选项。

**结论**

参数元数据至少需要描述数据类型、默认值、范围约束、步长、精度和资源选择方式。参数还可以由工具或运行环境动态提供候选值，例如扫描可用 GPU 后生成设备选项；动态参数的查询时机、刷新方式和当前值失效后的处理规则仍需确定。

### 27. 动态参数的刷新与失效

**问题**

动态参数（例如 GPU/CPU 设备列表）由谁提供并在什么时候刷新：打开参数面板时查询、工具初始化时查询，还是由用户点击刷新？如果项目保存的设备已经不存在，是否要求用户重新选择后才能运行？

**回答**

打开参数面板时自动查询动态参数。设备参数不硬性保存设备名称，而是保存设备序号，例如第 `0` 块卡；界面根据当前运行环境把序号映射为具体设备名称。

**结论**

动态参数的候选值在打开参数面板时刷新。GPU/CPU 设备选择在项目中保存稳定的逻辑标识或序号，显示层负责映射当前设备名称，不直接把设备名称作为绑定依据。设备数量或设备类型发生变化时的索引越界处理仍需确定。

### 28. 动态设备索引失效处理

**问题**

如果项目保存的设备序号在当前机器上不存在，例如项目保存第 `1` 块 GPU，但当前只有 `1` 块 GPU（只有序号 `0`），系统应该如何处理：自动选择默认设备、标记参数错误并禁止运行，还是允许工具初始化时自行处理？

**回答**

UI 照常传递索引/序号等参数，设备索引失效时由工具内部自行处理。

**结论**

UI 不负责根据当前设备数量改写项目中的设备索引，也不在界面层强制阻止运行。工具在初始化或执行时负责校验索引，并自行决定报错、降级或选择替代设备；处理结果通过工具的状态码和状态信息输出。

### 29. 外部资源路径与导出映射

**问题**

本机项目保存图像、模型等外部资源路径时，路径采用绝对路径还是支持项目相对路径？执行“导出”时，是否将这些资源复制到导出包，并自动把项目中的路径映射为导出包内的相对路径？

**回答**

本机保存时，UI 层参数设置的路径是什么就保存什么，绝对路径和相对路径都支持。导出时再自动将项目中的路径映射为导出包内的相对路径；导出功能不纳入首版，后续再设计。

**结论**

首版项目保存不强制转换外部资源路径，按 UI 当前值原样持久化。跨机器导出属于后续功能，届时负责资源复制和路径相对化映射。

### 30. 结果展示区的首版交互

**问题**

右上角结果展示区首版需要支持哪些内容和交互？例如显示原图、裁剪图、预处理图和 YOLO 结果；叠加矩形/多边形/点集/圆等 ROI；缩放、平移、适配窗口、图层显示隐藏；以及在图像上绘制或编辑 ROI 作为工具输入。

**回答**

结果展示区不区分原图、裁剪图和预处理图，工具返回什么图就显示什么图。首版支持显示 8U 彩色图、8U 灰度图、二值图等图像数据；图像上可以叠加 ROI。没有图层概念，但需要区分输入 ROI 和输出 ROI，可以使用不同颜色表示。支持在图像上绘制或编辑 ROI，并将其作为工具输入。检测框属于 ROI 的一种，不单独设计结果表格；类别和置信度等结果直接以多维数组展示，例如 `[[1, 2, 3], [1, 2, 3]]`。ROI 也使用多维数组表示，例如 `[[ROI_TYPE, x, y, w, h, angle]]`，其中 `ROI_TYPE` 按第 32 组协议规定：`1` 表示线、`2` 表示矩形、`3` 表示圆、`4` 表示多边形、`5` 表示点集；单个点不作为 ROI 类型。

**结论**

右上角应提供通用图像显示和交互画布，不按流程阶段预设固定视图。图像数据和 ROI 数据由工具输出驱动；输入 ROI 与输出 ROI 采用视觉颜色区分。首版不做图层管理和结果表格，数组数据以可读的多维数组形式展示。

### 31. ROI 编码与编辑规则

**问题**

ROI 数组协议是否统一使用固定字段顺序和固定长度，还是不同 `ROI_TYPE` 使用不同长度/形状？绘制或编辑 ROI 后，画布如何把像素坐标转换为工具输入坐标；输入 ROI 和输出 ROI 是否允许直接修改，还是只有用户创建的输入 ROI 可编辑？

**回答**

所有 ROI 统一使用 `[ROI_TYPE, ...参数]` 格式，不同 ROI 类型使用不同长度的参数数组。坐标直接使用图像像素坐标。只允许编辑输入 ROI，输出 ROI 只读显示。

**结论**

ROI 数据需要由统一协议解析和绘制，编辑器不能假定所有 ROI 具有相同参数长度。画布交互产生或修改的输入 ROI 直接写回图像像素坐标；输出 ROI 只用于展示和数据传递，不允许在画布上修改。

### 32. 首版 ROI 类型协议

**问题**

首版必须支持哪些 ROI 类型？请为每种类型确定 `ROI_TYPE` 编号和参数顺序，例如线、矩形、圆、点、多边形、点集等。多边形或点集的点数是否允许动态变化，采用扁平数组还是二维点数组表示？

**回答**

首版支持线、矩形、圆、多边形和点集，不把单个点作为 ROI 类型。ROI 使用 `float32` 扁平数组，首元素是使用整数值编码的 `ROI_TYPE`。具体协议为：`1` 线 `[1, x1, y1, x2, y2]`；`2` 矩形 `[2, 左上角x, 左上角y, width, height, angle]`；`3` 圆 `[3, cx, cy, radius]`；`4` 多边形 `[4, x1, y1, x2, y2, ...]`；`5` 点集 `[5, x1, y1, x2, y2, ...]`。坐标使用图像像素坐标。

**结论**

首版 ROI 数据模型支持五类几何类型、动态数量和动态点数。所有 ROI 使用 `float32` 扁平数组，单个点不作为独立 ROI 类型。工具端口和画布解析器统一按固定 `ROI_TYPE` 编号、字段顺序和像素坐标语义解析。

### 33. 结果展示对象选择

**问题**

当多个节点都输出图像或 ROI 时，右上角结果区如何决定显示哪个输出：显示当前选中节点的全部图像和 ROI、由用户从输出端口选择，还是固定显示流程末端节点的结果？是否需要同时查看多个节点的输出？

**回答**

显示流程图中当前选中节点的全部图像和 ROI 输出。结果展示区还包含缩略图区域，缩略图数量对应工具输入的图像批量数量。用户可以在缩略图区域选择要展示的图片，并查看该图片对应的 ROI。

**结论**

右上角结果区以当前选中节点作为数据上下文，展示其所有图像和 ROI 输出。批量图像需要按批量元素生成缩略图；主画布当前显示用户选中的批量元素，并只叠加与该图片对应的 ROI。多个图像输出端口在界面中的布局和批量维度不一致时的处理规则仍需确定。

### 34. 多图像输出与批量对应关系

**问题**

当前节点有多个图像输出端口时，结果区是否为每个图像输出提供独立显示区域，还是合并到一个区域中切换？如果多个输出的批量数量不同，是否要求它们必须一致，还是各自拥有独立缩略图选择？

**回答**

多个图像输出合并到一个显示区域，通过下拉菜单或标签切换。不同图像输出的批量数量由工具自行处理，UI 不额外规定数量对应关系。

**结论**

结果区只提供一个主图显示区域，通过输出选择控件切换当前图像输出；当前批量元素和 ROI 展示由所选工具输出的数据决定。工具负责处理多个图像输出之间批量数量不同的情况，界面不对其强行对齐。

### 35. Python 工具的进程边界

**问题**

内置 Python 工具和用户自定义 Python 工具运行时，Python 解释器是嵌入桌面软件主进程，还是每个工具/流程使用独立 Python 进程？如果 Python 脚本异常退出，是否允许直接影响主程序？

**回答**

不使用独立 Python 进程。Python 解释器嵌入 C++ 主进程，Python 工具由 C++ 子线程通过 `pybind11` 调用。Python 脚本异常时，工具应捕获异常，并通过状态码、状态信息展示出来。

**结论**

Python 工具嵌入桌面软件的 C++ 主进程，不创建独立 Python 工作进程。Taskflow/C++ 工作线程通过 `pybind11` 调用内置或用户 Python 工具；Python 异常需要转换成工具固定的非零状态码和状态信息，再按普通 DAG 数据传递给下游。Python 调用的 GIL 并发策略，以及解释器发生不可恢复错误时的主进程处理策略仍需确定。

### 36. Python 进程内的并发与恢复

**问题**

Taskflow 并行调度多个 Python 节点时，嵌入 C++ 主进程的 Python 解释器是否允许多个 C++ 工作线程同时调用不同工具实例？Python 脚本异常或解释器错误时，系统如何处理？

**回答**

Python 工具从 C++ 子线程通过 `pybind11` 调用。允许多个 C++ 工作线程进入 Python；每个线程按 `pybind11` 的 GIL 规则获取解释器访问权，实际并行程度由 CPython GIL 以及原生扩展是否释放 GIL 决定。

**结论**

Python 工具不再通过独立进程隔离或自动重启。Taskflow 可以并行调度不同 Python 节点，多个 C++ 工作线程可以进入嵌入式解释器，但每个线程必须遵守 GIL 获取规则；同一节点实例仍不允许并发调用。可捕获的脚本异常转换为非零状态码和状态信息；解释器级错误的处理策略待确认。

### 37. Python/C++ 数据交换

**问题**

Python 与 C++ 工具在同一进程内传递图像、ROI 和多维数组时，是否要求使用与 C++ 工具相同的统一数据类型、元素类型、维度和 `[B, N, ...]` 语义？绑定对象的内存所有权和生命周期如何约定？

**回答**

使用 `pybind11` 处理 Python 与 C++ 的数据交换。图像在 C++ 端使用 OpenCV `cv::Mat`，在 Python 端使用 `numpy.ndarray`，具体转换细节由 `pybind11` 定义。

**结论**

Python 工具桥接层以 `pybind11` 为基础，图像类型映射为 C++ `cv::Mat` 与 Python `numpy.ndarray`。ROI、标量/字符串多维数组和检测结果字段的 Python 映射类型，以及绑定对象的内存所有权和生命周期，需要在接口设计阶段依据 pybind11 规则进一步确定。

### 38. 非图像数据的 Python 映射

**问题**

ROI、多维标量数组、类别、置信度和状态信息在 Python 侧是否统一映射为 `numpy.ndarray` 或基础 Python 类型？是否要求 Python 工具直接接收和返回与 C++ 端同形状的 NumPy 数组，并保留 `[B, N, ...]` 维度信息？

**回答**

按统一方向处理：ROI、多维标量数组、类别和置信度等数组类数据使用 `numpy.ndarray`，保留 `[B, N, ...]` 形状；状态码使用 Python `int`，状态信息使用 Python `str`。字符串数组也遵循统一的 NumPy 数组映射约定。

**结论**

Python 工具桥接层需要保持与 C++ 端一致的数据类型和维度语义，数组类输入输出统一映射为 `numpy.ndarray`，状态输出映射为 `int` 和 `str`。具体 NumPy dtype、连续内存要求和 ROI 数组字段协议由公共数据类型规范确定。

### 39. Python 工具调用签名

**问题**

Python 函数式工具和类工具的固定调用签名如何定义？例如函数使用 `execute(inputs, parameters) -> outputs`，类使用 `initialize(parameters)`、`execute(inputs)`、`stop()`、`release()`；状态码和状态信息是否包含在每次方法返回值中，还是由运行时统一补充？

**回答**

函数式工具使用 `execute(inputs) -> outputs`，输入数据和输入参数都包含在 `inputs` 中。类工具使用 `initialize(inputs) -> outputs`、`execute(inputs) -> outputs` 和 `release() -> outputs`，不需要 `stop` 接口。

Python 工具使用 `dict` 作为输入和输出容器。输出包含 `status_code`、`status_message` 和其他工具输出，约定使用 `0`、`1`、`2`、`3` 等键：`0` 是状态码，`1` 是状态信息，其余键由工具自行定义。C++ 工具的输入和输出容器使用 `std::vector<std::any>`。

**结论**

函数式和类工具都采用统一的输入/输出容器思路，状态信息与业务输出同时返回。Python 使用字典键访问，C++ 使用 `std::vector<std::any>` 的位置访问；具体元数据如何把命名参数、端口和 C++ 向量位置对应起来仍需确定。

### 40. C++ 容器位置与工具端口映射

**问题**

C++ 工具使用 `std::vector<std::any>` 时，工具输入输出端口如何映射到向量位置？是否固定 `0` 为状态码、`1` 为状态信息、`2` 开始为业务输入/输出，并由 YAML 元数据声明每个位置的名称和类型？Python 字典是否也需要与同一组端口编号保持一致？

**回答**

输入和输出端口都在 YAML 中声明。C++ 输出容器固定使用 `outputs[0]` 表示状态码、`outputs[1]` 表示状态信息，这两个固定输出不需要在 YAML 中额外声明；其他业务输入和输出按 YAML 声明的位置、名称和类型映射。Python 容器保持相同的端口编号语义。

**结论**

YAML 是工具业务端口和参数的声明来源，运行时据此完成 UI、强类型连线和 C++/Python 容器位置映射。状态码和状态信息属于所有工具的内置系统输出，固定占用输出位置 `0`、`1`，不重复写入工具 YAML。

### 41. YAML 工具定义的组织与发现

**问题**

工具 YAML 元数据如何组织和加载：每个工具一个 YAML 文件，还是所有工具共用一个清单？软件启动时是否自动扫描固定目录并加载 YAML，内置工具和用户自定义 Python 工具是否使用相同的发现机制？

**回答**

每个工具使用一个 YAML 文件，内置工具和用户工具分别放在不同目录下。

**结论**

工具元数据采用“一工具一 YAML”组织方式，并按内置工具目录和用户工具目录分开管理。Python 脚本仍按既定固定目录加载，YAML 负责关联脚本文件及函数/类；目录扫描、刷新和定义冲突处理规则仍需确定。

### 42. 工具目录扫描与刷新

**问题**

软件什么时候扫描内置工具目录和用户工具目录：仅启动时扫描、打开工具库时扫描，还是提供工具库刷新操作？用户新增或修改 YAML 后，是否需要重启软件才能生效？

**回答**

软件启动时自动扫描固定目录并加载 YAML。通过界面直接修改工具配置时立即刷新，并写入 YAML；如果用户直接在外部修改 YAML，则需要重启软件重新扫描后才生效。

**结论**

工具系统首版不做外部 YAML 热加载。界面修改走“更新内存定义、刷新工具库、持久化 YAML”的流程；外部文件变更在软件重启时统一读取。工具定义冲突和唯一标识规则仍需明确。

### 43. 工具唯一标识与冲突

**问题**

每个工具是否需要独立的稳定 ID，项目节点保存工具 ID 而不是显示名称？当内置目录和用户目录出现同名或同 ID 工具时，如何处理：禁止加载、用户工具覆盖内置工具，还是同时加载并显示来源？

**回答**

每个工具类型有稳定且唯一的工具类型身份，例如图像读取工具可以有 `001` 或其他唯一标识。项目节点保存工具类型身份和节点序号；界面显示使用工具类型名和节点序号，例如“图像读取 - 001”。节点序号自增，删除节点后不复用已使用的序号。

**结论**

工具类型身份是工具定义本身的稳定身份，不由 YAML 文件路径、文件名或扫描顺序决定。项目节点在此基础上增加项目级不可复用的节点序号。项目文件和流程依赖引用工具类型身份及节点序号；界面使用保存的工具类型名和节点序号展示节点。工具目录出现重复工具类型身份时的加载冲突规则仍需确定。

### 44. 节点序号作用域与 ID 格式

**问题**

节点序号是在整个项目内统一递增，还是每种工具分别递增？组合 ID 采用什么格式，例如 `001-0001`、`001_0001` 或其他格式？节点序号是否在项目保存和重新打开后继续保持不变？

**回答**

节点序号在整个项目内统一递增。工具 ID 和节点序号分开存储，工具 ID 不对用户展示；界面最多显示工具名称和节点序号，例如 `图像读取-001`。项目保存和重新打开后，节点序号保持不变。

**结论**

节点序号是项目级不可复用序列，工具 ID 与节点序号是独立字段。工具 ID 用于 YAML、工具注册表和节点实现定位，用户可见名称使用工具显示名加节点序号，例如 `图像读取-001`；不要求展示工具 ID 或组合内部 ID。删除节点不回收序号，新建节点继续递增，项目重开后节点序号保持不变。

### 45. 工具 ID 冲突处理

**问题**

如果内置工具目录和用户工具目录中出现相同的工具 ID，软件启动扫描时如何处理：禁止冲突工具加载、用户工具覆盖内置工具、内置工具优先，还是同时加载但要求显示来源并使用不同的内部身份？

**回答**

扫描时优先加载内置工具，再加载用户工具；工具类型身份不由扫描过程临时生成，也不会因扫描顺序变化而改变。内置工具和用户工具不应使用同一个工具类型身份。

**结论**

工具加载顺序为内置工具优先、用户工具随后。工具类型身份必须由工具定义或注册信息稳定提供，而不是由扫描阶段按顺序生成；目录新增、删除、移动或重命名不能导致已有工具类型身份漂移。重复身份的具体冲突处理仍需另行定义。

### 46. 工具 ID 的稳定生成

**问题**

软件扫描 YAML 时，工具类型身份如何稳定提供？是否根据工具目录、YAML 文件路径或文件名生成固定 ID，并保证新增/删除其他工具不会重新编号已有工具？如果 YAML 文件被移动或重命名，是否视为新工具？

**回答**

工具类型身份不根据 YAML 文件路径或文件名生成。新增或删除其他工具不会影响已有工具类型身份；YAML 文件移动或重命名也不改变工具类型身份，只要文件内容中的工具类型定义/注册身份保持不变并且仍位于软件扫描的有效目录中。

**结论**

工具类型身份与 YAML 的路径/文件名解耦，也与扫描顺序无关。YAML 文件移动或重命名不是工具类型变更；只要软件重新扫描后仍能读取相同的稳定工具类型身份，原项目引用继续有效。只有工具定义被删除、未被扫描到、被禁用，或实际改变了工具类型身份时，项目节点才可能进入缺失状态。

### 47. 项目打开时工具缺失

**问题**

如果项目保存的工具类型身份在重新打开时已经不可用，例如对应工具定义被删除、未被扫描到或被禁用，项目应该如何处理：打开失败、保留为不可执行的缺失工具节点，还是自动尝试按工具名称或 YAML 新路径匹配？YAML 文件单纯移动或重命名但工具类型身份不变时，不应视为缺失。

**回答**

项目打开时保留为缺失工具节点。只要项目中存在缺失节点，整个流程就禁止运行，而不是只禁止缺失节点自身运行。

**结论**

工具缺失不能阻止项目打开。即使工具定义不可用，节点仍保留项目保存的工具类型名、节点序号、参数、连线和其他可见信息，并以缺失状态显示；这些信息用于识别和修复节点，不代表节点仍可执行。只要项目中存在缺失节点，流程整体不可运行。YAML 文件移动或重命名但工具类型身份不变时，不进入缺失状态。缺失节点的修复和替换规则仍需确定。

### 48. 缺失工具节点的修复

**问题**

用户为真正缺失的工具节点重新指定一个有效工具定义时，是否保留原节点序号、参数和连线？如果新工具的输入输出类型与原工具不兼容，是禁止替换，还是允许替换后由用户重新调整连线和参数？

**回答**

重新绑定时保留原节点序号；兼容的参数和连线可以保留，不兼容的参数和连线清空。

**结论**

缺失节点恢复时不改变其项目节点序号。重新绑定工具后，系统按新旧工具的参数和端口类型进行兼容性检查，保留兼容项，清空不兼容参数和连线；项目在所有缺失节点处理完成后才可运行。单纯修改 YAML 文件路径或文件名不需要重新绑定，只要原工具类型身份仍可被扫描到。

### 49. 工具定义变更与项目兼容

**问题**

如果工具 YAML 在项目保存后被修改，例如删除输入/输出端口、修改参数类型或改变参数范围，项目重新打开时是否按同样的兼容性规则处理：保留兼容配置，清空不兼容参数和连线，并禁止存在不兼容项的流程运行？

**回答**

保留兼容配置，清空不兼容参数和连线。工具定义发生变化时不禁用流程运行，而是由工具内部处理并可能返回错误状态；同时弹窗告知用户工具已更新。

**结论**

工具缺失和工具更新采用不同策略：缺失工具会使整个流程禁止运行；已存在但定义发生变化的工具仍允许流程运行，系统清理不兼容配置并提示用户，具体运行错误由工具自身通过状态码和状态信息处理。

### 50. 工具更新的检测方式

**问题**

项目如何判断工具定义是否发生更新：保存工具 YAML 的版本号、修改时间、文件路径/名称，还是保存 YAML 内容指纹并在打开项目时比较？工具更新提示是否在项目打开时弹出，并列出受影响的节点、参数和连线？

**回答**

项目保存 YAML 内容指纹/hash。打开项目时比较当前工具定义的指纹；如果工具已更新，则弹窗提示，并列出受影响的节点，不需要列出具体参数和连线变化。

**结论**

项目通过工具 YAML 内容指纹识别工具更新。更新提示发生在打开项目时，提示内容以受影响节点为主；参数兼容性和连线清理按工具加载规则执行，不在弹窗中展开细节。

### 51. 项目文件格式与保存内容

**问题**

项目文件本身采用什么格式：YAML、JSON、二进制或其他格式？除工具 ID、节点序号、节点参数、端口连线和外部资源路径外，是否还保存流程图布局、运行流程勾选状态、当前选中状态、缩放位置、窗口布局等编辑器状态？

**回答**

项目文件采用 YAML。保存工具 ID、节点序号、节点参数、端口连线、外部资源路径、流程图布局、节点位置和运行流程勾选状态；不保存当前选中状态、缩放比例、当前标签页和窗口布局。

**结论**

项目 YAML 持久化流程本身、编辑器画布布局以及多流程项目的运行流程勾选状态；不持久化当前选中节点、当前标签页、缩放比例和窗口布局等临时界面状态。缩放比例和窗口布局只在当前软件进程内有效，不保存布局配置；软件重启后恢复默认布局。

### 52. 项目 YAML 版本兼容

**问题**

项目 YAML 是否需要包含项目格式版本号？旧版本项目打开时是否自动迁移到当前格式；如果项目版本高于当前软件版本，是否禁止打开、只读打开，还是允许忽略未知字段后打开？

**回答**

项目包含格式版本号。首版暂不处理兼容机制，后续版本允许对项目格式进行破坏性修改。

**结论**

项目 YAML 需要保存格式版本号，但首版只保证当前版本读写，不提供旧版本迁移或高版本兼容策略。版本兼容和迁移作为后续能力处理。

### 53. 流程编辑器基本操作

**问题**

首版流程编辑器除了拖拽工具、移动节点和连线外，是否必须支持撤销/重做、删除节点、复制/粘贴、框选多节点、自动布局和连线删除？其中撤销/重做是否覆盖参数修改、节点移动和连线变更？

**回答**

首版支持拖拽创建工具节点、移动节点、复制/粘贴节点、框选多个节点和删除节点。节点之间的输入关系不通过用户直接绘制真实连线建立，而是在参数设置区域中为输入参数选择上游输出；连线只在 UI 上作为依赖关系显示。首版不支持撤销、重做和自动布局。

**结论**

流程图编辑以节点和输入参数配置为主，连线是由输入参数引用关系推导出的可视化结果，而不是独立可编辑对象。删除节点时需要同步处理引用该节点输出的输入参数和显示连线，具体删除后的引用处理仍需确定。

### 54. 参数区建立输入依赖

**问题**

在参数设置区域为输入参数选择上游输出时，候选列表是否只显示类型和维度兼容的输出？每个输入参数是否只能选择一个上游输出；一个上游输出是否允许被多个下游输入复用；取消选择后是否立即删除对应的显示连线？

**回答**

候选列表只显示类型和维度兼容的输出。每个输入参数只能选择一个上游输出，一个上游输出可以被多个下游输入复用；取消选择后立即删除对应的显示连线。

**结论**

输入依赖由参数配置建立，连接候选在 UI 层按强类型和维度过滤。连接关系是一对多可复用的输出引用，输入端口是一对一绑定；显示连线始终由当前参数引用关系推导。

### 55. 删除节点后的输入引用

**问题**

删除一个被其他节点引用的上游节点时，下游输入参数如何处理：自动清空引用并删除显示连线、保留为缺失引用并禁止流程运行，还是弹窗要求用户先处理所有下游引用后才能删除？

**回答**

删除被引用的上游节点时，自动清空所有下游输入引用，并删除对应的显示连线。

**结论**

删除节点会同步清理所有指向该节点输出的输入参数引用。下游节点和其他参数保留，只有受影响的输入引用及其显示连线被删除；由于首版没有撤销功能，该行为需要立即生效并持久化。

### 56. 节点复制与粘贴

**问题**

复制/粘贴节点时，新节点是否获得新的项目级节点序号？节点参数是否完整复制；原节点的输入引用、输出被其他节点引用的关系，以及框选多个节点时节点之间的内部引用是否一并复制？

**回答**

新节点获取新的项目级节点序号，完整复制手动输入的参数。上层工具的输出引用不复制，其他节点对原节点输出的引用关系也不复制。软件一次只能打开一个项目，不支持粘贴到新项目。

**结论**

复制/粘贴只复制节点本身及其手动配置，不复制任何外部输入引用或下游引用。粘贴结果是当前项目中的新节点，并使用新的不可复用节点序号；跨项目剪贴板操作不纳入首版。

### 57. 多选节点内部引用

**问题**

复制多个节点时，如果被复制节点之间原本存在输入引用，是否也不复制这些内部引用，所有新节点的输入引用都清空；还是保留选中节点之间的内部引用，仅清空指向选区外部节点的引用？

**回答**

保留选中节点之间的内部引用，只清空指向选区外部节点的引用。

**结论**

多选复制时，系统需要复制选区子图，并将内部输入引用重映射到新节点；所有指向选区外部节点的输入引用清空。复制后的子图保持内部拓扑，但不携带外部依赖。

### 58. 工具库分类与搜索

**问题**

左上角工具库的分类是否固定为采集、处理、预处理、后处理、系统、深度学习等，还是由工具 YAML 定义分类？首版是否需要工具搜索、分类筛选、收藏或最近使用？

**回答**

工具 YAML 按三级目录存储：第一级是大类，例如系统、处理、预处理、深度学习；第二级是子类，例如目标检测、语义分割；第三级是具体工具。工具库支持搜索栏，对工具名称进行模糊搜索；不需要收藏、最近使用和标签功能。

**结论**

工具分类由 YAML 所在的三级目录体现，目录结构同时作为左上角工具库的层级导航。首版搜索只针对工具名称做模糊匹配，不引入标签、收藏和最近使用等额外索引。

### 59. 工具库条目展示信息

**问题**

工具库中每个具体工具条目需要显示哪些信息：工具名称、描述、版本、实现语言、输入/输出端口、图标、YAML 文件路径和脚本/注册接口信息？哪些信息只在参数区或工具详情中显示？

**回答**

工具库只显示工具名称和可为空的图标。流程图中的节点显示工具名称、节点序号和版本号，例如 `图像读取-001-v1.0`，也可以把版本号放在工具 UI 右下角以小号字体显示。C++ 或 Python 实现方式不在工具库或节点 UI 中显示。输入/输出端口在参数区域以参数组件形式显示。

创建或修改工具的 UI 弹窗显示工具英文名（唯一）、函数工具或类工具类型、Python 脚本文件及函数/类名称、YAML 文件名。C++ 注册接口名称只在代码中使用，不在 UI 中显示；注册时保持与工具英文名一致。

**结论**

用户界面隐藏实现语言和 C++ 注册细节，分别在工具库、节点 UI、参数区域和工具定义弹窗展示对应信息。工具英文名是跨 YAML、Python 调用和 C++ 注册的一致标识；工具版本需要作为可显示的独立元数据，具体来源和更新规则仍需确定。

### 60. 工具版本号规则

**问题**

工具版本号由谁维护、保存在哪里、采用什么格式？例如 `v1.0` 是否写入 YAML 并由用户在工具编辑弹窗中修改；工具定义或实现发生变化时是否需要手动递增版本号，版本号是否参与项目兼容检查？

**回答**

版本号写入 YAML，可以由工具创建/修改弹窗维护，采用 `v1.0` 这类格式并手动递增。版本号变化会触发工具更新提示；兼容检查时，如果参数类型兼容则保持现状，否则断开连接。

**结论**

工具版本是 YAML 元数据的一部分，由用户显式维护。版本变化与 YAML 内容指纹变化一样会触发项目打开时的更新提示。端口连接兼容性以参数类型为核心：兼容时保留连接，不兼容时自动断开；数组维度、端口删除和其他字段的具体兼容规则仍需明确。

### 61. 工具更新的兼容判定

**问题**

工具更新时，兼容判定是否同时检查端口方向、基础数据类型、数组维度、ROI 类型和参数类型？参数范围、默认值、显示名称或工具版本变化是否只提示更新，不断开已有连接？新增端口是否保留为空并允许流程继续运行？

**回答**

参数类型改变或参数/端口删除时断开连接。新增参数、参数范围变化和默认值变化时弹窗提示，但流程继续允许运行，由工具内部自行处理是否报错或正常运行。

**结论**

工具更新兼容规则按变化类型区分：会影响数据契约的类型改变和删除操作自动断开连接；新增参数、范围和默认值变化不自动阻止流程，也不自动断开连接，只在项目打开时提示用户，运行结果由工具状态输出决定。

### 62. 未连接输入的运行规则

**问题**

如果工具定义了输入参数，但项目中没有为该输入选择上游输出，点击运行时如何处理：禁止整个流程运行并提示未连接输入、向工具传递类型对应的空值，还是允许工具自行处理未连接输入？

**回答**

输入参数未连接时允许运行，由工具自行处理空值。

**结论**

运行器不因未连接输入阻止流程，也不要求输入必须来自上游节点。未连接输入需要以对应类型的空值传给工具，工具自行判断是否可以继续或返回错误状态。未连接输入和上游节点输出的空数组/空字符串都属于工具可处理的数据状态。

### 63. 画布输入 ROI 的绑定

**结论**

### 85. Python 工作进程的数据通信边界

不使用独立 Python 进程，而是在 C++ 子线程中通过 `pybind11` 处理。

**结论**

第 35、36 组关于独立 Python 进程和进程自动重启的旧结论全部废止。最终采用嵌入式 Python：C++ 主进程初始化 Python 解释器，Taskflow 工作线程通过 `pybind11` 调用 Python 工具；Python 工具与 C++ 工具共享主进程，Python 异常由工具转换为状态输出。第 87 组已确定多个 C++ 工作线程可以进入解释器，具体并发程度受 GIL 和原生扩展规则约束；仅解释器级故障处理仍待确定。

### 87. 嵌入式 Python 的并发策略

**问题**

Taskflow 可能在多个 C++ 工作线程中同时调度独立 Python 节点。考虑 CPython GIL，平台是否全局串行化 Python 调用，还是允许多个 C++ 工作线程进入 Python 解释器？

**回答**

允许多个 C++ 工作线程进入 Python，由 GIL 和 `pybind11` 管理；原生扩展释放 GIL 时可以并行。每个流程节点实例仍不允许并发调用。

**结论**

运行器保留跨节点并行调度能力。每个 C++ 工作线程调用 Python 前必须正确获取 GIL，并在调用完成后释放；Python 字节码受 CPython GIL 约束，使用 NumPy、OpenCV 或其他释放 GIL 的原生扩展时才可能真正并行。节点实例级互斥规则继续有效，不能因为不同线程可以进入解释器而并发调用同一个工具实例。

### 88. 嵌入式 Python 的不可恢复错误

**问题**

普通 Python 脚本异常可以由工具捕获并转换为非零状态码。若发生解释器级错误、原生扩展崩溃或其他不可恢复错误，软件是否应将当前 Python 节点标记为错误，并继续执行下游和其他节点？

**回答**

将当前 Python 节点标记为错误，继续执行下游和其他节点。

**结论**

产品层希望采用错误继续传播策略：Python 节点发生错误后，节点输出非零状态码和状态信息，下游继续执行。对于可捕获的 Python 异常，这一策略可以由工具运行器实现；但真正的解释器致命错误或原生扩展崩溃可能无法被 C++ 捕获，且可能使嵌入式 Python 或整个主进程处于不安全状态。在“不使用独立 Python 进程”的约束下，必须在实现阶段明确可恢复错误与进程级致命错误的边界，不能承诺所有不可恢复错误都能安全地标记节点后继续运行。

### 89. Python 错误继续策略的适用边界

**问题**

在嵌入式 Python 架构下，产品希望 Python 节点错误后继续执行下游；对于无法安全捕获的解释器崩溃或进程级致命错误，是否仍要求继续执行？

**回答**

**结论**

节点级错误继续传播的保证范围限定为可捕获的 Python 异常、工具返回错误和可识别的原生调用错误。解释器崩溃、进程级致命错误或无法保证运行时完整性的情况允许终止应用，不要求伪装成节点错误继续执行。该边界与嵌入式 Python、无独立进程隔离的架构一致。

### 90. Python/C++ 数据的内存策略

**问题**

在同一进程内通过 `pybind11` 传递 `cv::Mat` 和 `numpy.ndarray` 时，输入和输出是否都复制，还是输入尽量零拷贝、输出复制为 C++ 自有数据？

### 92. 可写输入的分支隔离

**问题**

当一个允许 Python 原地修改的零拷贝输入被多个下游分支复用时，运行器是否自动复制或禁止连接，还是由工具作者自行保证不会产生并发写入？

**结论**

### 93. Python/C++ 公共数据的 dtype 与内存布局

**问题**

Python 与 C++ 之间传递图像和数组时，数据类型与内存布局由平台统一规定，还是由每个工具端口单独声明？运行器是否自动进行 dtype、通道或非连续内存转换？

**回答**

平台定义数组的元素类型、维度和内存布局规则；图像端口统一使用通用 `Image` 类型承载 `cv::Mat`，不在平台层限制其具体 dtype、通道数或通道顺序。DAG 数据传递不做隐式转换。

**结论**

Python/C++ 公共数据协议由平台统一定义基本表示和校验规则，不允许工具绕过端口契约发明数组连接兼容规则。数组必须使用端口声明的元素类型、维度和 C-contiguous 内存布局；图像端口只校验数据属于通用 `Image`/`cv::Mat` 类型，不校验具体 dtype、通道数或通道顺序。运行器不在 DAG 数据传递中做隐式 dtype、通道顺序或数组布局转换；工具需要转换时，必须在工具内部或显式的预处理工具中完成。结果展示区可以为了 Qt 显示而显式转换为 `uint8`，该转换不改变节点缓存中的原始图像数据。

### 94. 首版图像数据协议

**问题**

首版图像数据的核心传输是否严格限制为 `uint8`、固定通道数和固定通道顺序？Qt 结果展示是否可以单独将图像转换为便于显示的 `uint8` 格式？

**回答**

核心图像数据不严格限制为 `uint8`。Qt 结果展示时使用 `uint8` 格式方便显示；批量图像在 C++ 侧使用 `std::vector<cv::Mat>`。

**结论**

首版不将核心图像数据限制为 `uint8`、`CV_8UC1` 或 `CV_8UC3`。图像端口统一使用通用 `Image` 类型，允许任意 `cv::Mat` 对象连接；dtype、通道数、通道顺序、尺寸和连续性由工具自行解释和处理。批量图像在 C++ 运行时使用 `std::vector<cv::Mat>` 表示，单张图像尺寸可以由工具实际数据决定。Qt 结果展示区为便于显示，可以把当前图像显式转换为 `uint8` 显示副本，但不得用该显示副本覆盖节点缓存中的原始图像。DAG 运行器不因显示需要自动改写业务数据。

### 95. 图像端口的类型契约

**问题**

图像端口是否需要在 YAML 中声明具体 dtype、通道数和通道顺序，还是统一使用通用图像类型并允许任意 `cv::Mat` 对象连接？

**回答**

图像端口统一只声明为 `Image`，任意 `cv::Mat` 都可连接，由工具自行处理。

**结论**

图像端口采用开放的通用 `Image` 类型，平台只确认对象是 `cv::Mat`，不因 dtype、通道数、通道顺序、尺寸或连续性不同而禁止连接。工具负责解释输入图像并在需要时显式转换；平台不在连接或运行器数据传递阶段隐式转换图像。数组、ROI 和标量等非图像端口继续按强类型和维度规则校验。

### 96. `cv::Mat` 的 Python 映射

**问题**

任意 `cv::Mat` 在 Python 工具侧如何映射？批量 `std::vector<cv::Mat>` 是否要求图片尺寸一致并堆叠为单个数组，还是保留每张图片的独立对象？

**回答**

单张图像映射为保留 dtype、shape、通道和 strides 的 `numpy.ndarray`；`std::vector<cv::Mat>` 映射为 `list[numpy.ndarray]`，允许批量图片尺寸不同。

**结论**

`pybind11` 图像绑定保留每个 `cv::Mat` 的 dtype、形状、通道信息和 strides，不强制堆叠或复制为统一形状的 NumPy 数组。单张图像对应一个 `numpy.ndarray`，批量图像对应一个 `list[numpy.ndarray]`，因此不同批量元素可以拥有不同尺寸、通道数或 dtype。输出仍按第 90 组规则复制为 C++ 运行时拥有的数据。

### 97. Python 输入视图的生命周期

**问题**

零拷贝输入映射成的 `numpy.ndarray` 是否允许 Python 工具在 `execute` 返回后继续保存和使用？如果需要跨调用保存，是否由运行器自动保活或复制？

**回答**

只保证在本次工具调用期间有效。工具不得跨调用持有输入视图，需要长期保存时必须自行复制。

**结论**

运行器只在当前 Python 工具调用期间保证零拷贝输入视图有效。工具返回后，Python 不得继续持有或使用该 `numpy.ndarray` 视图；需要跨调用、跨轮次或保存到实例成员时，工具必须显式复制数据。运行器不为输入视图自动保活，也不因 Python 工具持有引用而延长 C++ 缓存生命周期。

### 98. Python 输出的所有权转换时机

**问题**

Python 工具返回 `numpy.ndarray`、图像列表或其他业务输出后，运行器应何时将其转换为 C++ 自有数据并写入节点缓存？是否允许缓存继续持有 Python 对象或其底层视图？

**回答**

Python 工具返回后立即复制/转换为 C++ 自有数据，转换完成后才写入节点缓存；缓存不持有 Python 对象或底层视图。

**结论**

Python 工具输出必须在本次调用返回后立即转换为 C++ 运行时拥有的数据。转换完成前不得提交节点输出缓存；节点缓存只保存 C++ 自有对象，不保存 Python 对象、NumPy view 或依赖 Python 解释器生命周期的底层内存。

### 99. Python 输出转换失败

**问题**

如果 Python 工具返回值无法按 YAML/端口契约转换为 C++ 数据，例如类型错误、数组维度不匹配、非法 `cv::Mat` 视图或输出缺失，运行器应如何处理节点缓存和下游输入？

**结论**

Python 输出无法按端口契约转换为 C++ 数据时，直接走统一的节点失败路径：运行器将该节点标记为错误，清空该节点已有的业务输出缓存，并为本轮下游输入构造对应类型的空值。下游仍按错误继续传播规则执行，不增加独立的转换失败状态或专门的流程分支。工具自身返回可被正常转换的业务错误时，仍按第 84 组由工具决定业务输出保留或清空。

### 100. ROI 变长数据的容器表示

**问题**

已有结论确定 ROI 使用 `[ROI_TYPE, ...参数]`，支持线、矩形、圆、多边形和点集，并允许每张图片的 ROI 数量不同、每个多边形/点集的点数不同。首版应如何表示这种变长数据？

**结论**

ROI 的逻辑容器采用嵌套变长数组，不使用固定形状 padding，也不要求所有图片具有相同的 ROI 数量。数据结构表示为批量图片列表、每张图片的 ROI 列表，以及每个 ROI 独立的 `float32` 扁平参数数组；多边形和点集可以拥有不同的点数。五类 ROI 的编号和字段顺序按第 32 组协议固定。

### 101. ROI 数值数组的标量类型

**问题**

在已确定的嵌套变长 ROI 数组中，`ROI_TYPE` 与坐标参数如何放入同一个扁平数组？

**回答**

**结论**

每个 ROI 的扁平参数数组统一使用 `float32`。数组首元素存放 `ROI_TYPE` 的整数值，后续元素存放像素坐标、尺寸、角度或动态点坐标。C++ 和 Python 侧必须保持相同的 `float32` 表示；解析器按 ROI 类型把首元素转换为整数语义，不改变底层数组类型。

### 102. InferRT 的 CMake 集成方式

**问题**

首版 YOLO C++ 工具使用 InferRT `dev` 分支时，VisionRT 是直接把 InferRT 源码加入自身构建，还是依赖已经安装/构建好的 InferRT SDK？VisionRT 的 CMake 如何发现并链接 InferRT？

### 104. YOLO 节点的批量输入语义

**问题**

首版 YOLO C++ 工具接收上游图像时，是只支持单张 `cv::Mat`，还是接收 `std::vector<cv::Mat>` 批量输入？当批量图片尺寸不同或模型要求固定输入尺寸时，预处理和输出批量对应由谁负责？

### 105. YOLO 检测坐标的映射

YOLO 内部把不同尺寸图像转换为模型输入尺寸后，检测框坐标应以哪一个坐标系输出？

不固定具体版本，只要求 Windows + NVIDIA 环境可运行。

**结论**

首版不固定具体 NVIDIA GPU 型号、驱动版本、CUDA 版本、TensorRT 版本或 InferRT SDK commit。产品基线是可运行的 Windows + NVIDIA 环境；具体工具在运行时负责检查自身所需的模型、GPU、CUDA、TensorRT 和 InferRT 兼容性，并通过节点状态码和状态信息报告问题。平台启动诊断应展示实际检测到的运行环境，但不以全局固定版本规则阻止软件启动。

### 109. 运行环境不兼容的反馈方式

**问题**

在不固定 GPU、驱动、CUDA、TensorRT 和 InferRT 版本的前提下，如果环境不满足某个工具的运行要求，平台和工具应如何反馈？

**回答**

工具初始化或执行失败，节点显示红色错误；详细原因写入该节点的状态信息/错误日志输出。

**结论**

运行环境不兼容由具体工具在初始化或执行时检查并报告，不作为软件启动级错误。对应节点进入红色错误状态，详细原因通过该节点固定的状态信息/错误日志输出展示；下游按既定错误继续传播规则执行，平台不额外生成流程级错误，也不因单个工具环境不兼容阻止其他节点或应用启动。

### 110. 四区布局的可调整性

**问题**

第 51 组已经确定项目 YAML 不保存窗口布局，窗口布局由软件运行时管理。本组只确认四区工作台的交互：参考截图采用左侧工具库/流程图、右侧结果/参数的四区结构，首版是否允许拖动分隔线调整区域大小、折叠面板或恢复默认布局？

**回答**

允许拖动调整大小，但不支持折叠和恢复默认布局；不保存布局配置，软件重启后恢复默认布局。

**结论**

四区工作台支持拖动分隔线调整各区域大小，不支持面板折叠，也不提供单独的恢复默认布局操作。调整结果只在当前软件进程内有效，不写入项目 YAML 或其他布局配置；软件重启后恢复默认四区布局。运行期间仍允许拖动分隔线，因为这不改变流程参数、节点结构或输入引用。

### 111. 四区面板的最小尺寸

**问题**

四区支持拖动分隔线但不支持折叠时，各区域是否设置最小宽度/高度，以避免工具名称、流程节点、结果画布或参数控件被压缩到不可用？

**回答**

每个区域设置合理的最小宽度/高度，拖动到下限后停止，保证内容始终可操作。

**结论**

四区面板均设置合理的最小宽度和高度。用户拖动分隔线到下限后不能继续压缩，工具库条目、流程图节点、结果画布和参数控件必须保持可操作。最小尺寸由界面实现根据内容需要确定，并与应用最小窗口尺寸一致。

### 112. 应用窗口的最小尺寸

**问题**

当窗口缩放可能使四区同时低于最小尺寸时，应用应如何处理？

**回答**

设置应用最小窗口尺寸，禁止继续缩小。

**结论**

应用设置最小窗口尺寸，保证四区面板的最小宽度和高度始终成立。窗口达到该尺寸后，操作系统不允许继续缩小；不采用窄窗口滚动或自动改为其他布局。

### 113. 首次启动的项目状态

**问题**

工程师首次启动软件或当前没有打开项目时，主界面应直接进入哪种状态？

**回答**

直接打开空白项目，默认创建一个空流程 `流程1`。

**结论**

首次启动或当前没有打开项目时，软件直接进入空白项目，不显示额外欢迎页或项目选择页。空白项目默认包含一个名为 `流程1` 的空流程，工程师可以立即从工具库拖拽节点开始搭建。项目文件仍需通过显式保存操作写入磁盘。

### 114. 未保存修改的处理

**问题**

工程师修改项目后执行新建、打开其他项目、关闭软件或复位时，如果当前项目尚未保存，软件应如何处理？

**回答**

弹窗询问“保存 / 不保存 / 取消”。

**结论**

工程师修改项目后执行新建、打开其他项目、关闭软件或复位时，如果当前项目存在未保存修改，软件统一弹窗提供“保存 / 不保存 / 取消”。选择“取消”终止当前操作；选择“保存”成功写入后继续操作；选择“不保存”丢弃当前修改后继续操作。复位也遵循同一规则。

### 115. 单项目中的流程数量

**问题**

参考截图左下角存在 `流程1` 标签和流程选择器。一个项目是否可以包含多个流程？运行和保存时，流程之间如何处理？

**回答**

一个项目可以包含多个流程，以标签页切换；各流程默认并行运行。流程之间如果需要交互，例如一个流程中的数据传输工具等待另一个流程中的工具数据，由工具层负责阻塞和数据传递，流程之间仍保持并行。

**结论**

项目支持多个独立流程，每个流程以标签页表示，工程师通过标签页切换当前查看的流程。各流程在运行时默认并行调度；流程间交互不建模为平台级 DAG 连线或流程拓扑，而由工具层面的数据传输/等待工具实现。某个流程等待另一个流程的数据时，只阻塞相关工具调用，不改变其他流程继续运行的能力。项目 YAML 需要保存所有流程及其各自布局，节点序号仍按第 44 组使用项目级不可复用序列。

### 116. 多流程项目的运行作用域

**问题**

当项目包含多个流程时，顶部“运行流程”操作应启动哪些流程？停止、循环运行和复位对多个流程的作用域是否一致？

**回答**

启动项目内全部选中的流程并行运行；停止、循环运行也作用于全部选中的流程。通过一个可展开的流程选择控件，以复选框勾选需要运行的流程。

**结论**

多流程项目的运行作用域由流程选择集合决定。点击“运行流程”时，所有已勾选流程并行启动；“停止”和“循环运行”作用于同一批已选流程。左下角提供可展开的流程选择控件，通过复选框管理运行选择。标签页用于切换当前查看的流程，复位仍按第 22 组重启软件并重新打开当前项目。

### 117. 流程查看与运行选择

**问题**

当前标签页表示正在查看的流程，流程选择控件表示要运行的流程。两者是否保持独立？例如工程师查看“流程 A”时，仍可以勾选“流程 B”参与运行。

**回答**

完全独立，可以查看流程 A，同时运行流程 B；标签页切换不改变运行勾选。

**结论**

当前查看的流程与运行选择集合完全独立。工程师可以在查看流程 A 的同时勾选并运行流程 B，切换标签页不会自动改变任何流程的运行勾选状态。运行期间流程选择仍属于运行配置，按第 80 组与流程参数/结构一起锁定；只允许查看和切换标签页。

### 118. 流程页的管理操作

**问题**

多流程项目中的流程页是否支持新增、重命名、关闭/删除和复制？删除当前流程或最后一个流程时如何处理？

**回答**

支持新增、重命名、删除和复制流程；项目至少保留一个流程，删除当前流程后自动切换到相邻流程。

**结论**

多流程项目支持新增、重命名、删除和复制流程。项目至少保留一个流程，不能删除最后一个流程；删除当前流程后自动切换到相邻流程。流程复制沿用节点复制的内部引用重映射语义，复制出的流程获得独立的流程身份和节点序号，跨流程交互引用是否复制需按后续跨流程数据传输规则确定。

### 119. 跨流程数据传输的等待语义

**问题**

流程间可以通过工具层面的数据传输工具交互。若接收工具在等待另一个流程的工具数据时，数据尚未产生，等待是否有超时或停止边界？该问题需要与第 23 组“停止时等待当前工具完成”保持一致。

**回答**

由工具参数定义有限超时；超时后工具返回节点错误和空输出。停止操作仍等待当前工具调用返回。

**结论**

跨流程数据传输工具的等待超时由工具自身参数定义，不由流程运行器统一规定。接收工具在超时时返回非零状态码、状态信息和对应类型的空业务输出；下游按错误继续传播规则执行。停止操作不强制中断等待中的工具调用，仍等待当前工具按超时或数据到达后返回，符合第 23 组工具无 `stop` 接口的规则。

### 120. 跨流程数据传输的寻址方式

**问题**

跨流程数据传输工具需要等待另一个流程中某个工具的某个输出时，发送端和接收端如何建立对应关系？

**回答**

由工具参数指定流程名和节点名，输出端口由工具自行解释。

**结论**

跨流程数据传输的来源关系不使用平台普通输入端口引用模型。接收工具通过自身参数保存目标流程名和节点名，目标输出端口由工具内部解释和处理；平台不替跨流程关系建立端口级强类型连接，也不自动为该关系绘制普通 DAG 连线。跨流程引用的有效性、数据类型和输出端口解析由工具负责。

### 121. 跨流程引用失效处理

**问题**

当跨流程数据传输工具参数中指定的流程名或节点名被重命名、删除，或目标输出端口发生变化时，平台应如何处理该参数？

**回答**

平台不改写也不清理参数，由工具初始化/执行时自行判断并返回节点错误；项目仍可保存。

**结论**

跨流程目标流程或节点被重命名、删除，或输出发生变化时，平台不自动同步或清空接收工具的跨流程参数。工具在初始化或执行阶段自行解析目标并判断引用是否有效；无效时按普通节点失败处理，通过节点状态码和状态信息报告错误，项目仍允许保存。

### 122. 跨流程数据的轮次与缓冲

**问题**

在连续运行或多个流程并行运行时，跨流程数据传输工具可能面对多次发送、接收速度不同和多个待处理数据。发送数据与接收数据的轮次匹配、队列或最新值保留策略由谁定义？

**回答**

由数据传输工具自行定义轮次匹配、队列、丢弃和最新值策略，平台只负责调度工具。

**结论**

连续运行中的跨流程数据语义完全由数据传输工具负责。工具自行决定发送数据与接收数据的轮次匹配方式、是否排队、队列容量、丢弃规则以及读取最新值或历史值；平台不提供统一跨流程队列、轮次配对或缓存覆盖规则，只负责按已选流程调度工具。

### 123. 复制流程时的跨流程参数

**问题**

复制一个包含跨流程数据传输工具的流程时，工具中指定的目标流程名、节点名和其他跨流程参数如何处理？

**回答**

原样复制跨流程参数，目标流程名、节点名和端口信息保持不变，由工具继续解析。

**结论**

复制流程时，跨流程数据传输工具中的目标流程名、节点名、输出端口信息和其他参数原样复制。平台不分析、不重映射跨流程引用；复制后的工具仍由自身解析这些参数，并根据目标流程当前是否运行、是否有数据及自身超时策略处理结果。

### 124. 已选流程依赖未选流程

**问题**

如果已选中的接收流程依赖一个未勾选的发送流程，点击运行时平台是否自动启动发送流程，还是严格只运行已勾选的流程？

**回答**

严格只运行已勾选的流程，不自动启动未勾选流程；接收工具按自身规则等待并可能超时。

**结论**

多流程项目运行时严格遵循工程师的勾选集合。平台不因跨流程引用自动启动未勾选的发送流程，也不禁止已选接收流程启动；接收工具根据自身等待、空数据和超时策略处理未得到发送数据的情况。

### 125. 多流程项目的节点序号

**问题**

第 44 组确定节点序号在整个项目内统一递增且删除后不复用。项目支持多个流程后，这条规则是否仍适用？复制流程或在不同流程新增节点时，节点序号如何分配？

**回答**

继续全项目统一递增；不同流程新增或复制节点都使用全项目下一个未使用序号。

**结论**

多流程项目继续使用第 44 组的项目级节点序号规则。所有流程共享同一个不可复用的递增序列；在任意流程新增节点、复制节点或复制流程时，都分配项目范围内下一个未使用序号。流程删除不回收序号，已有节点序号在项目保存和重新打开后保持不变。

### 126. 运行流程选择的初始状态

**问题**

项目新建、打开或复位后，流程选择控件中的运行复选框应如何初始化？运行选择是否写入项目 YAML？

**回答**

运行勾选状态保存在项目文件中。新建项目默认勾选，打开或复位后按项目文件中保存的状态进行勾选。

**结论**

运行流程勾选状态属于项目配置，随项目 YAML 保存。新建项目中的流程默认全部勾选；打开已有项目或复位后，按项目文件中保存的勾选状态恢复。运行选择与当前查看标签页、当前选中节点和窗口布局相互独立；后几项仍不保存。

### 127. 运行选择变更的保存状态

**问题**

运行流程勾选状态属于项目 YAML 配置时，工程师修改勾选状态后是否立即将项目标记为“有未保存修改”？

**回答**

修改勾选后立即标记项目为未保存，关闭、打开、复位时按第 114 组提示。

**结论**

运行流程勾选状态发生变化后，项目立即进入未保存状态。关闭软件、打开其他项目、新建项目或复位时，统一按第 114 组弹窗询问保存、不保存或取消；只有保存项目后，新的运行选择才写入 YAML。

### 128. 运行缓存是否写入项目

**问题**

节点业务输出缓存、状态码、状态信息和节点运行状态在运行中会保留。保存项目、关闭软件或复位时，这些运行时数据是否也写入项目 YAML？

**回答**

不写入项目 YAML；重新打开或复位后缓存为空、节点状态为灰色未运行。

**结论**

节点业务输出缓存、状态码、状态信息和运行状态全部属于内存运行时数据，不写入项目 YAML。保存项目只保存流程配置、节点参数、输入引用、流程布局、节点位置和运行流程勾选状态；项目重新打开或软件复位后，所有节点缓存为空，节点状态恢复为灰色未运行。

### 129. 四区默认比例

**问题**

软件新建项目、打开项目或重启后恢复默认四区布局时，工具库、流程图、结果展示和参数区应采用什么默认空间比例？

**回答**

左侧占约 36%，右侧占约 64%；左上工具库约 38% 高、左下流程图约 62% 高；右上结果区约 58% 高、右下参数区约 42% 高。

**结论**

软件新建项目、打开项目或重启后恢复默认四区布局时，水平区域默认按左侧约 36%、右侧约 64% 分配；左侧垂直区域按工具库约 38%、流程图约 62% 分配；右侧垂直区域按结果展示约 58%、参数区约 42% 分配。实际分隔线位置受面板最小尺寸约束，布局调整不保存，重启后恢复该默认比例。

### 130. 未选中节点时的参数区

**问题**

当流程图中没有选中节点时，右下角参数区应显示什么内容？

**回答**

参数编辑区保持为空，但显示参数分组标签，例如预处理、检测、后处理；具体分组内容和完整分组定义后续开发时再确定。

**结论**

流程图没有选中节点时，右下角不显示任何节点参数值或项目基本信息，参数编辑内容保持为空。参数区仍可显示预留的分组标签，例如预处理、检测、后处理，以保持工作台结构稳定；分组的具体名称、数量、顺序和内容不在本轮设计中展开，后续开发时确定。

### 131. 未选中节点时的结果区

**问题**

当流程图中没有选中节点时，右上角结果展示区应显示什么内容？

**回答**

保持空白，只显示结果区工具栏和输出选择控件。

**结论**

流程图没有选中节点时，右上角主显示区域保持空白，不显示任何节点缓存或默认图像，也不自动选中节点。结果区工具栏和输出选择控件仍保留，以维持稳定的工作台结构；没有可选输出时控件不产生结果内容。

### 132. 无图像输出节点的结果区

**问题**

当工程师选中的节点没有图像输出，只有 ROI、标量数组、字符串数组或状态输出时，右上角结果展示区如何处理？

**回答**

主图区域保持空白；ROI 无图像可叠加时不显示，数组和字符串继续在右下角输出参数中查看。

**结论**

选中的节点没有图像输出时，右上角主图显示区域保持空白；没有关联图像的 ROI 不在主图上绘制。状态码、状态信息/错误日志、标量数组、字符串数组和其他非图像输出继续由右下角输出参数区域展示，不因结果区没有图像而隐藏或自动回退到上游图像。

### 133. 节点参数区的内容组织

**问题**

选中一个工具节点后，右下角参数区同时需要展示输入参数、工具配置参数和输出参数。这三类内容应如何组织？

**回答**

类似参考软件，参数区分为输入参数区和输出参数区。输入参数区位于左侧，参数可以按业务分组，例如“基本输入”“检测参数”“结果处理”等。工程师可以在输入参数区域直接建立与上层工具输出的依赖，通过下拉列表等控件选择具体的上游工具及其具体输出参数；候选项仍遵循第 54 组确定的类型和维度兼容规则。

输出参数区位于右侧，只读显示节点运行结果、工具状态码和状态信息，并提供“数据”和“关系”两个视图标签。数据视图显示输出参数及其结果值；关系视图显示当前节点各输出与下游节点的依赖关系，并显示连接到下层的数量，同时提供从关系视图发起下游连接的操作入口。

**结论**

选中节点后，右下角采用左输入、右输出的稳定双区结构。输入参数区支持按业务分组展示和编辑，并通过端口级选择器绑定上游输出；工具配置参数作为输入参数区中的可编辑参数分组呈现，不另设与输入区并列的顶层面板。输出参数区只读，使用“数据/关系”标签切换：数据视图用于查看运行结果、状态码和状态信息，关系视图用于查看各输出的下游引用数量和依赖关系，并提供创建下游依赖的快捷入口。底层项目模型仍只有第 54 组定义的输入引用关系，关系视图的连接操作不能引入第二种独立连线模型。

### 134. 关系视图的下游连接操作

**问题**

在输出参数区的“关系”视图中点击“连接下游工具”时，这个操作具体如何建立依赖：是打开一个向导，让工程师选择已有下游节点、下游输入参数和当前输出参数并完成绑定；还是允许直接从当前输出端拖出独立连线，再由系统补充或推断下游输入参数？如果一个输出可连接多个下游节点，是否沿用第 54 组的一对多规则，并在类型不兼容时只显示可用的下游输入？

**回答**

工程师在输出参数区的“关系”视图中，对某个具体输出参数执行右键操作，软件弹出级联二级菜单。一级菜单列出工具，二级菜单列出对应工具的参数；只有与当前输出参数类型匹配的下游参数才显示为可选项。

**结论**

关系视图的连接入口绑定到具体输出参数，而不是整个节点。右键输出参数后，通过“工具 → 工具参数”的二级菜单选择目标依赖，平台按当前输出与目标输入的类型契约过滤菜单项。选择完成后，系统建立第 54 组定义的下游输入引用，并据此更新流程图中的依赖关系和输出参数的下游数量；不引入独立于输入引用之外的连线数据模型。一条输出仍可被多个下游输入复用，一个下游输入仍只能绑定一个上游输出。

### 135. 关系菜单中的工具对象

**问题**

关系视图右键菜单的一级“工具”具体指什么：当前流程图中已经存在的下游节点，还是工具库中的工具类型？如果同一种工具在流程图中存在多个节点，菜单如何区分它们？选择二级参数后，是直接绑定已有节点，还是先按工具库定义自动创建一个新节点并完成绑定？

**回答**

一级菜单只列出当前流程图中已经存在的工具节点，不从工具库中创建新节点。同一种工具存在多个节点时，使用“工具名称 - 节点序号”区分具体节点。选择二级参数后，直接将当前输出参数绑定到所选节点的匹配输入参数。

**结论**

关系视图右键菜单的目标范围是当前流程，不跨流程查找节点，也不负责创建节点。一级菜单项对应一个已有节点，显示为“工具名称 - 节点序号”；二级菜单项对应该节点的输入参数，仅显示与当前输出类型匹配的参数。选择参数后直接写入该输入参数的上游引用，流程图依赖关系由该引用重新计算。跨流程数据传输继续遵循第 120 组的工具参数寻址方式。

### 136. 关系菜单绑定已占用输入

**问题**

当关系视图中选择的下游输入参数已经绑定了其他上游输出时，当前输出参数再次选择该输入应如何处理：直接替换原绑定、弹窗确认后替换，还是将该输入从菜单中隐藏/禁用并要求先在输入参数区解除原绑定？替换时是否需要同步更新原上游输出的关系数量和流程图显示？

**回答**

已绑定其他上游输出的下游输入参数从关系视图的级联菜单中隐藏。若需要把它绑定到当前输出，工程师必须先在下游节点的输入参数区解除原绑定，再从当前输出参数的关系菜单重新选择该输入。解除绑定后，原上游输出的关系数量和流程图中的依赖显示同步更新。

**结论**

关系菜单只提供当前未绑定的下游输入参数。平台不在关系菜单中直接替换已有引用，也不弹窗执行隐式替换；改绑必须经过“输入参数区解除原绑定 → 输出参数关系菜单重新绑定”的显式流程。每次解除或建立引用都要立即刷新两端的关系视图、关系数量和流程图依赖显示。

### 137. 关系视图数量与明细

**问题**

输出参数的关系视图显示的“下游数量”按什么统计：按下游工具节点数量统计，还是按具体的“下游节点输入参数绑定”数量统计？如果同一个下游节点有两个输入参数都连接到当前输出，是否显示为 1 个下游工具但列出 2 个参数，还是显示为 2 条关系？关系视图是否同时列出已建立的下游节点名称、节点序号和输入参数名称？

**回答**

按具体的下游输入参数绑定关系计数。同一个下游节点的两个输入参数都连接到当前输出时，关系数量显示为 `2`。关系视图只显示数量，不显示下游节点、节点序号或输入参数明细。

**结论**

输出参数关系视图的数量统计单位是一条输入引用关系，即“当前输出参数 → 一个下游节点的一个输入参数”。同一节点的多个输入分别计数；关系视图只展示总数量，不提供已建立关系的明细列表。建立或解除任一引用后，数量立即更新。

### 138. 关系菜单与环检测

**问题**

关系视图的级联菜单会列出当前流程中的已有节点，但某些节点可能会因当前拓扑形成有向环。例如当前输出所属节点已经位于候选节点的下游，继续绑定会形成环。此类节点应从一级菜单中隐藏，还是保留但禁用并说明“会形成环”？如果当前输出与候选输入的类型不匹配，是否也采用相同的隐藏策略？

**回答**

关系视图只允许从当前工具的输出参数向下一节点的输入参数建立连接，不允许从当前工具反向连接上一节点的输入参数。因此上一层工具不应作为关系菜单的候选项，不需要通过菜单让工程师处理反向连接。

**结论**

关系菜单具有固定的流程方向：只能建立“当前工具输出 → 下一层工具输入”的依赖，不能建立指向上游工具输入的反向依赖。关系菜单不提供上游节点作为候选项；工具类型不匹配的输入参数也不提供为可选项。编辑器仍应在保存、加载或内部修改依赖关系时进行 DAG 合法性检查，防止非法项目数据绕过界面规则进入运行时。

### 139. “下一节点”的范围

**问题**

关系菜单中的“下一节点”是指当前节点在流程拓扑中任意可达的下游节点，还是只指画布上紧邻当前节点的直接下一节点？例如当前节点 `A` 后面已经存在 `B → C`，从 `A` 的输出建立关系时，是否可以直接选择 `C` 的输入，还是必须先连接 `B`，再由 `B` 连接 `C`？

**回答**

允许连接任意下游节点。例如当前节点为 `A` 时，可以直接把输出连接到 `C` 的输入，不要求先建立 `A → B` 再建立 `B → C`。

**结论**

关系视图允许当前输出参数直接绑定当前流程中任意下游节点的匹配输入参数，不要求目标节点在画布上与当前节点相邻，也不要求存在中间节点关系。建立关系后，依赖方向仍记录为“当前工具输出 → 下游节点输入”；关系数量按第 137 组规则按绑定关系计数。

### 140. 未建立关系时的下游节点判定

**问题**

当两个节点之间尚未建立任何依赖时，平台如何判定目标节点是否属于当前输出的“下游节点”？关系菜单是否列出当前流程中除当前节点外的所有节点，再排除当前节点的上游节点和已占用输入；还是根据画布从左到右的位置、节点序号或其他流程顺序来判定？如果两个节点尚无路径关系，是否允许先建立任意方向的第一条连接？

**回答**

使用网格画布上的垂直位置判定方向。对当前输出参数打开关系菜单时，排除 `y` 值小于当前节点或与当前节点处于同一 `y` 值位置的节点；只有位于当前节点下方、`y` 值更大的节点才属于可选的下游节点。网格画布用于保持节点位置和行的判定稳定。

**结论**

在尚未建立依赖关系时，平台以网格画布的纵向坐标定义候选方向：目标节点的 `y` 值必须大于当前节点的 `y` 值。目标节点位于当前节点上方或同一行时，不出现在关系菜单中；位于下方的节点才继续接受工具参数类型匹配和输入占用状态过滤。该规则允许直接连接任意更下方节点，不要求节点相邻或存在中间关系。

### 141. 建立关系后的节点移动

**问题**

如果已经建立了 `A → C` 的输入引用，之后工程师拖动节点导致目标节点 `C` 移到 `A` 上方或与 `A` 同一行，原有关系应如何处理：保留已建立的关系，只禁止新的反向连接；自动删除或解除该关系；还是保留关系但显示方向/布局警告，要求工程师手动处理？

**回答**

禁止通过拖动节点破坏已有关系的纵向顺序。对于已经建立的 `A → C` 关系，不允许把 `C` 拖到 `A` 上方或与 `A` 处于同一 `y` 值位置。

**结论**

已有输入引用同时形成节点的画布布局约束：对每条“上游输出 → 下游输入”关系，目标节点必须保持在来源节点下方，且不能处于同一行。工程师拖动节点时不能使下游节点移动到上游节点上方或同一 `y` 值位置；已建立的关系不因布局操作被自动解除。

### 142. 非法拖动的交互反馈

**问题**

当拖动节点即将违反已有上下游的纵向位置约束时，界面应如何反馈：将节点限制在最后一个合法位置并禁止继续拖动；允许拖动但在释放时自动回到原位置；还是弹出提示后取消本次移动？如果一个节点同时连接多个上游或下游节点，是否必须同时满足所有关系的纵向约束？

**回答**

节点拖动到最后一个合法位置后停止，继续向非法方向拖动无效。

**结论**

节点移动采用实时边界限制。拖动过程中如果继续移动会违反已有上下游关系的纵向顺序，节点保持在最后一个合法位置，软件不弹出提示，也不在释放后回弹；已有依赖关系保持不变。一个节点同时存在多条上下游关系时，所有关系是否共同参与位置限制另行确认。

### 143. 多条关系的纵向约束

**问题**

当一个节点同时连接多个上游或下游节点时，节点移动是否必须同时满足全部关系？例如 `A → C`、`B → C` 时，`C` 必须位于 `A` 和 `B` 两者下方；`C → D`、`C → E` 时，`C` 必须位于 `D` 和 `E` 两者上方。若多个约束产生不同边界，是否取能够同时满足所有关系的合法范围？

**回答**

必须同时满足所有关系的纵向约束。如果本次移动没有能够同时满足全部关系的合法网格位置，则保持节点原位置，禁止本次移动。

**结论**

节点移动时，所有已建立的上下游关系同时生效。节点必须位于每一个上游节点下方，并且位于每一个下游节点上方；多条关系共同决定可移动的合法 `y` 范围。若存在共同合法范围，节点只能在该范围内移动；若不存在共同合法网格位置，则保持节点原位置，禁止本次移动。

### 144. 网格间距不足时的节点移动

**问题**

如果一个节点同时受到多个上游和下游的约束，导致上下游之间没有可用的网格行，例如节点必须低于某个上游、又高于某个下游，但两者之间没有合法网格位置，软件应如何处理：保持节点原位置并禁止本次移动；自动移动相关节点以腾出空间；还是允许节点暂时处于非法位置并提示布局问题？

**回答**

自动移动相关节点，为当前节点腾出满足纵向约束的网格空间。

**结论**

当节点移动会受到网格行空间不足的影响时，软件自动调整相关节点的位置，尝试腾出合法网格空间；调整后所有已有关系仍必须满足第 143 组确定的纵向约束，不能通过暂时破坏关系来完成移动。若调整后仍不存在共同合法网格位置，则保持节点原位置，禁止本次移动。自动调整只改变画布布局，不改变节点、输入引用或流程拓扑。自动移动的具体传播范围和多分支场景下的移动顺序仍需确认。

### 145. 自动移动相关节点的传播范围

**问题**

自动腾出网格空间时，“相关节点”的范围如何定义？例如链路 `A → B → C` 中拖动 `B` 向下，如果 `B` 与 `C` 的间距不足，是否递归推动 `C` 以及 `C` 后面的所有下游节点；如果一个节点有多个上游或下游，是否推动所有受影响的直接和间接节点？自动移动时是否保持被推动节点的相对水平位置和相对顺序不变？

**回答**

不需要递归推动所有受影响的直接和间接下游节点。

**结论**

自动腾挪不沿流程拓扑递归扩散到整条下游链，只对局部相关节点进行处理。直接关系节点的具体处理范围，以及被移动节点的水平位置和相对顺序是否需要保持，仍需进一步确定。

### 146. 自动腾挪的局部范围

**问题**

既然不递归推动所有间接下游节点，第 144 组中的“相关节点”是否限定为当前被拖动节点的直接上游和直接下游节点？如果只调整这些直接关系节点后仍没有合法网格位置，是否保持当前节点原位置并禁止本次移动？

**回答**

自动腾挪只做满足约束所需的最小移动。如果直接上游和直接下游无法移动，且周围也无法腾出合法网格空间，则当前被拖动节点无法移动，保持在原位置。

**结论**

节点拖动触发的自动布局调整采用局部、最小移动原则，不递归推动所有直接和间接下游节点。系统优先尝试调整当前节点附近、与其直接上下游关系相关的节点；只有在能够通过局部调整满足全部纵向约束时才提交位置变化。若直接上游、直接下游及周围可调整节点均无法腾出合法网格空间，则拒绝当前节点移动并保持原布局。自动腾挪不改变节点序号、输入引用或流程拓扑。

### 147. 最小移动的判定标准

**问题**

“最小移动”具体按什么标准判定：优先移动节点数量最少，还是优先让节点的总位移距离最小？如果两种方案都可行，是否优先保持直接上下游节点不动，再选择距离最小的方案？自动移动是否只能沿 `y` 轴调整，保持节点的 `x` 坐标不变？

**回答**

自动腾挪同时考虑移动节点数量和位移距离：先保证移动的节点数量最少；在移动节点数量相同的方案中，再选择总位移距离最小的方案。

**结论**

自动腾挪的优化顺序为：第一优先级是移动节点数量最少，第二优先级是在节点数量相同的情况下使总位移距离最小。该规则用于局部可行方案之间的选择；自动移动的坐标轴范围仍需确认。

### 148. 自动腾挪的坐标轴

**问题**

自动腾挪时是否只调整节点的 `y` 坐标，以保持网格画布中的水平列和节点 `x` 坐标不变？还是允许同时调整 `x` 坐标，只要最终满足纵向关系约束并符合第 147 组的最小移动规则？

**回答**

允许同时调整 `x` 和 `y` 坐标。

**结论**

自动腾挪可以同时调整相关节点的水平和垂直位置。调整后的节点仍必须满足全部上下游关系的纵向约束；节点移动数量和总位移距离继续按照第 147 组的优先级选择方案。自动腾挪的总位移距离如何在网格坐标中计算仍需确认。

### 149. 网格位移距离的计算

**问题**

第 147 组中的“总位移距离”如何计算？是按网格横向步数与纵向步数之和（曼哈顿距离），按直线距离（欧氏距离），还是只比较位移后的网格步数而不计算几何距离？如果多个方案的节点数量和总距离都相同，是否保持原有节点相对顺序并任选其中一个可行方案？

**回答**

总位移距离采用横向网格步数与纵向网格步数之和，即曼哈顿距离。

**结论**

自动腾挪方案的总位移距离按网格曼哈顿距离计算：每个被移动节点的横向网格步数加纵向网格步数，再汇总所有被移动节点的位移。方案选择仍先比较移动节点数量，再比较总曼哈顿距离；当两项都相同时的最终选择规则仍需确认。

### 150. 等价腾挪方案的选择

**问题**

### 152. 网格位置冲突

禁止节点重叠。

### 156. 工具类型身份与缺失节点（修正）

**问题**

为什么项目中还会显示缺失工具节点，以及 YAML 文件重命名是否会导致工具缺失？

**回答**

节点显示名称由项目中保存的工具类型名和节点序号组成，例如“工具名称 - 001”。因此，即使工具定义暂时不可用，节点仍可以显示原来的名称、序号、参数和关系；这只是一个保留配置的缺失节点，不表示工具仍然可以执行。工具类型身份与 YAML 文件路径或文件名无关，单纯重命名 YAML 文件不会导致工具缺失；只有工具定义未被扫描到、被删除/禁用，或工具类型身份实际发生变化时，才会进入缺失状态。

**结论**

“缺失工具”指工具定义不可用，而不是节点名称消失。项目节点持久化工具类型身份、工具类型名、节点序号、参数和依赖关系，因此缺失时仍按“工具类型名 - 节点序号”显示。YAML 文件路径或文件名只是发现位置，不是工具身份；重命名或移动 YAML（且仍在有效扫描目录内）不影响原项目引用。重新绑定入口和替换工具的具体交互暂不作为本轮问题。

由平台固定分组。

**结论**

右下角输入参数区的顶层分组由平台统一定义，工具 YAML 和用户自定义 Python 工具不能创建任意新的顶层分组。工具参数需要归入平台提供的固定分组；固定分组的完整清单和最终排序由平台界面规范确定，不由单个工具自行改变。

### 158. 工具更新后的未保存状态

**问题**

打开项目时，如果检测到工具 YAML 已更新，并且平台按照第 49 组规则清理了不兼容参数或输入引用，这些内存中的清理结果是否立即将项目标记为“有未保存修改”，并要求工程师保存后才写回项目 YAML？如果只是提示工具更新但没有任何配置被清理，是否不标记未保存？

**回答**

检测到工具定义更新后，项目标记为未保存。工程师保存项目时，将更新后的工具指纹以及兼容性处理后的项目配置写回项目 YAML；软件不强行要求工程师立即保存，可以继续编辑或按未保存项目的常规规则处理关闭、打开和复位。

**结论**

工具定义更新被视为项目配置发生变化。打开项目时完成工具更新检测和兼容性处理后，项目进入未保存状态；保存操作才持久化新的工具指纹、清理后的参数和输入引用。平台不修改工具自身的 YAML 文件，也不在检测到更新时强制弹出保存流程。

### 159. 端口顺序与 C++ 容器位置

**问题**

工具元数据中的输入/输出端口名称、参数类型与 C++ 工具使用的 `std::vector<std::any>` 位置如何对应？是否由 YAML 中端口声明的固定顺序决定位置，并要求 C++ 函数或类工具严格按照该顺序读取输入、写入业务输出，状态码和状态信息固定占用预定义位置？

**回答**

在 YAML 中增加字段，显式声明每个业务输入/输出字段的顺序。运行时按照 YAML 声明的顺序，将端口名称、类型与 C++ 容器的位置进行映射；C++ 工具按该位置读取输入和写入业务输出。状态码和状态信息继续使用平台固定的输出位置，不由业务字段顺序覆盖。

**结论**

端口位置不依赖 YAML 文本中的偶然排列，也不由工具实现自行决定；每个业务字段必须在 YAML 中声明明确的顺序字段，运行时据此生成稳定的 `std::vector<std::any>` 位置映射。Python 字典仍按端口名称访问，但与 C++ 端共享同一套端口定义和位置语义。状态码固定为输出位置 `0`，状态信息/错误日志固定为输出位置 `1`；业务输出从后续位置开始，并按照 YAML 的字段顺序排列。

### 160. 端口顺序变更后的项目兼容

**问题**

如果工具 YAML 后续调整了业务输入/输出字段的声明顺序，但字段名称和类型没有变化，项目重新打开时应如何处理：按字段名称和类型保留原有参数、连接和项目配置，并重新生成新的容器位置；还是把顺序变化视为工具定义不兼容，清理相关参数和连接？

**回答**

字段顺序发生变化时，先按字段名称和类型判断兼容性。类型兼容则保留原有连接；类型不兼容则断开对应连接。顺序变化只影响运行时容器位置映射，不单独导致连接失效。

**结论**

工具定义更新时，业务字段的稳定匹配依据是字段名称和类型兼容性，而不是字段在 YAML 中的旧位置。字段顺序变化后，平台重新按照新顺序生成 C++ 容器位置映射；名称和类型兼容的参数、输入引用及输出关系继续保留，类型不兼容的对应连接断开。被断开的连接按普通配置变化处理，并使项目进入未保存状态；该规则与第 158 组的工具更新保存语义一致。

### 161. 多图像输出的批量缩略图

**问题**

当当前节点有多个图像输出，且不同输出的批量数量不同，结果区切换图像输出时，缩略图区域应如何处理：随当前图像输出切换为该输出自己的缩略图列表；固定使用当前节点的一套缩略图并对缺失批量项显示空白；还是禁止切换到批量数量不同的图像输出？

固定使用一套缩略图。切换图像输出时不改变缩略图列表；如果当前输出没有对应的批量项，则对应位置显示空白。

**结论**

结果区对当前节点使用一套固定的批量缩略图索引，缩略图数量沿用第 33 组已确定的工具输入图像批量数量。切换不同图像输出时沿用同一组缩略图和当前选中的批量索引，不因输出端口切换而重建缩略图列表；当前输出缺少对应批量项时，主图区域显示空白。

### 162. 多图像输出的批量一致性（修正）

**问题**

为什么同一节点的多个图像输出会返回不同的批量数量？对于当前产品的图像处理语义，它们是否都应表示同一批输入图像，并共享相同的批量数量 `B` 和批量索引语义？

**回答**

正常情况下没有理由返回不同的批量数量。同一节点的多个图像输出应表示同一批输入图像的不同结果，第 `i` 个输出图像对应第 `i` 个缩略图。只有工具明确具有筛选、合并或拆分批次等特殊语义时，才可能产生不同批量数量；这不作为当前首版图像流程的正常场景。

**结论**

首版同一节点的多个图像输出默认共享相同的批量数量 `B` 和批量索引语义，结果区使用这套批量索引生成固定缩略图。平台不为正常工具输出推断或补齐不同的批量数量；如果某个工具具有改变批量结构的特殊语义，应由工具自身明确声明和处理，不由通用界面猜测对应关系。原第 162 组关于从最大批量、第一个输出或输入图像推导缩略图数量的问题撤回。

### 168. 节点卡片上的执行耗时与底部流程耗时显示

**问题**

参考截图中，流程图各个节点卡片左下角显示了单次执行耗时（例如 `68.48ms`、`78.53ms`），界面左下角状态栏也显示了 `流程运行时间: xx ms`。首版是否需要实现节点级执行耗时统计与流程总耗时统计并显示在 UI 上？

**回答**

需要支持：运行时自动统计每个节点的单次执行耗时（以 ms 为单位显示在节点卡片左下角），同时统计并刷新当前流程的整体运行耗时（显示在界面左下角状态栏）；且每个节点需要区分工具算法耗时，以及其他耗时（例如数据准备/预处理、后处理、界面刷新等）。

**结论**

首版需要统计并展示执行耗时：
1. **流程级**：底部状态栏显示当前流程整体运行总耗时（单位 ms）。
2. **节点级**：每个节点卡片左下角显示该节点的单次运行耗时（单位 ms）。
3. **分项统计**：运行时需要对节点的耗时进行细分，区分工具自身核心算法耗时与框架层/前后处理/数据拷贝/界面刷新等其他耗时。分项耗时的具体呈现位置与交互方式仍需进一步确认。

### 169. 节点分项耗时的展示位置与形式

**问题**

当节点区分“核心算法耗时”与“其他耗时（如数据预处理、后处理转换、界面刷新等）”时，这些细分耗时应该在界面上的什么位置展示？

**回答**

节点卡片左下角显示该节点总耗时，鼠标悬停在卡片或耗时标签上时弹出 Tooltip 显示耗时明细（算法耗时、数据准备/预处理、后处理/转换、界面刷新等），右下角输出参数无需列出各分项耗时。

**结论**

节点耗时的展示形式为：
1. **默认常驻显示**：节点卡片左下角以紧凑标签常驻显示该节点的总执行耗时（如 `68.48ms`）。
2. **悬停明细 Tooltip**：当鼠标悬停在节点卡片或耗时标签上时，弹出 Tooltip 浮窗，详细列出分项耗时：核心算法耗时、数据准备/预处理耗时、后处理/数据转换耗时、界面刷新耗时等。
3. **输出参数区保持整洁**：右下角输出参数区域不额外将分项耗时列为输出行，专注于展示业务输出、状态码与状态信息。

### 170. 工具库向流程图添加节点的交互与网格放置规则

**问题**

**结论**

### 171. 流程图连线的视觉呈现与颜色规则

### 175. 参数区“▶ 执行”按钮的单工具运行行为与状态反馈

**问题**

**回答**

单工具即时执行：仅执行当前选中的单个工具节点；采用当前配置的用户输入与已绑定的上游最近一次输出缓存（若无缓存则传入对应类型的空值）；执行后即时刷新该节点的运行状态圆点、卡片耗时、右上角图像/结果区以及右侧输出参数表。

**结论**

单工具执行机制如下：
1. **执行范围**：严格仅执行当前流程图中选中的单个工具节点实例，不触发其上游前置节点或下游后续节点。
2. **输入来源**：
   - 用户输入模式的参数：使用参数区当前填写的最新值或画布绘制的 ROI；
   - 上层输入模式的参数：直接读取已连接上游节点的最近一次输出缓存；若上游节点尚未运行或无缓存，则按端口数据契约构造对应类型的空值（如空图像、空数组 `[]`、空字符串 `""` 等）传入，由工具自身处理。
3. **即时联动刷新**：工具执行返回后，系统立即：
   - 更新该节点在流程图中的运行状态圆点（成功为绿、错误为红）与卡片左下角耗时标签；
   - 刷新右上角结果展示区的主图像与叠加 ROI；
   - 刷新右下角输出参数区的“数据”结果值（包括工具状态码、详细状态信息及各项业务输出）。
